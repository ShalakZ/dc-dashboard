# W7h: a real first-load screen Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The owner (2026-10-12 night, roadmap row O-24) sees a blank white page and a bare "loading…" line on a refresh. Now the navy top bar and sidebar are painted as soon as the stylesheet is there (a static copy inside `index.html`), React swaps that copy for the same shell as a skeleton while the two auth requests are out, and the real shell replaces it without moving the bar, the sidebar or the content origin.

**Architecture:** Front end only. Nothing under `backend/` changes, no migration, no API change. One new component `src/components/AppShellSkeleton.tsx`, built from the real shell classes (`.shell`, `.navbar`, `.brand`, `.bar-in`, `.frame`, `.side`, `.nav-groups`, `.nav-group`, `.nav-heading`, `.side-row`, `.side-foot`, `main`) so the geometry is the real CSS's. `RequireAuth` renders it instead of the bare line and owns the one `TopProgress`. `index.html` holds a static copy of its markup (classes only) inside `#root`; `public/theme-init.js` (already the first script, external) sets `data-shell="expanded|minimized"` on `<html>` unless the path is `/login` or `/setup`, and CSS shows the static copy only under that attribute.

**Tech Stack:** React 19, react-router 7, TanStack Query 5, plain CSS (`@layer w6` plus the unlayered `themes.css`), Vitest + Testing Library, Playwright (controller only).

## Decisions taken here (the owner may overrule; none blocks the build)

1. **H1 to H5, H7 of the brief stand**, refined by the rest of this list.
2. **H6 (the two auth requests in parallel) is NOT done.** It would save one round trip once per page load and touches `AuthProvider` (authentication code). The static shell and the skeleton remove the blank page, which is the owner's complaint. Cost if wrong: one extra round trip of skeleton on a slow link; it can be added later as its own small task.
3. **The shell skeleton's `main` holds a bare status line and NO grey shapes (plan review C1; this deviates from H1's "content area as a PageSkeleton").** The Opus review measured that an `instant` shell region (or any region that counts as "seen") makes every skeleton of a refresh's chain instant: "Loading the page", the fleet summary, the asset tree, the asset and the chart all appear at opacity 1, which breaks W7f's no-flash rule and `e2e/w7f.spec.ts:451-467` and `:511-541`. A fading shell region cannot work either: the static copy would have faded in before React and React's replacement would restart the fade (a blink). Also on `/assets*` the real `main` has no padding (`main:has(.assets-layout)`), so shapes drawn in the skeleton's `main` would jump 28 px at the hand-over. So `main` holds only `<div role="status" aria-busy="true"><span class="sr-only">Loading</span></div>` (not an `.sk-region`, no animation); the navy bar and sidebar with their placeholders are the visible fix for the blank white page, and the page's own skeleton fades in after 150 ms exactly as in W7f. `Skeleton.tsx` is NOT touched (no `instant` prop). Cost if wrong: during the auth wait the content area is empty white under a calm navy shell; shapes can be added later with an `instant` region plus an update of `w7f.spec.ts`.
4. **The status is the bare line in `main`** (decision 3): `role="status"`, `aria-busy="true"`, one `sr-only` word "Loading". The bar and the sidebar (and their placeholders) are `aria-hidden` with nothing focusable (no skip link, no tab stops). It is the ONLY status of the shell skeleton. A `role="status"` element takes no accessible name from its content, so tests find it as `getByRole("status")` plus the text "Loading" (W7f's way), never `{ name: "Loading" }`.
5. **Classes only, no `style` attribute, no text node** in the shell skeleton's markup (it is copied into `index.html`, where a future strict `style-src` would drop a `style=""` attribute, while the React-set CSSOM styles of the other skeletons are exempt). Widths and heights come from classes `sk-w-<n>` (width in `ch`) and `sk-h-<n>` (height in px) added to `app.css` for exactly the sizes used. The brand name "DC Dashboard" is drawn by CSS (`.sk-shell .brand .lbl::before { content: "DC Dashboard" }`) so no test or reader finds a word in the skeleton. Cost if wrong: none (visible result is the same).
6. **Colours: tokens only.** Placeholders on the navy ground use `--side-bg-hover` (shine `--side-bg-active`); the quick-find box uses the real `--top-find-bg` and `--top-find-border`; the avatar circle `--side-bg-hover` (not the gold `--side-avatar-bg`). All eight looks come from the existing tokens; no new colour, no `--accent` inside `.navbar`/`.side` rules (the existing `app.css.test.ts` check stays green).
7. **The sidebar's state is the real one.** `AppShellSkeleton({ sidebar = initialSidebar() })` puts it in `data-sidebar` (the same function `Layout` uses, so the width cannot differ). For the static copy, `theme-init.js` mirrors `initialSidebar()` (ES5: the narrow query `(max-width: 1179.98px)`, then `localStorage["dcdash.sidebar"] === "minimized"`) into `data-shell`, and `app.css` carries a twin of each `.shell[data-sidebar="minimized"] …` rule that the skeleton's classes use, written `:root[data-shell="minimized"] .sk-shell[hidden] …` (scoped to the static copy, see decision 8, so the React skeleton follows only its own `data-sidebar` and the two inputs can never disagree on screen). The existing rules are NOT edited (an `:is()` group would raise their specificity). `sidebarState.ts` exports `SIDEBAR_KEY` and `NARROW_QUERY`; a test fails if `theme-init.js` stops matching them, and a CSS test fails if a minimized rule loses its twin (declarations equal). The roles are unknown during the auth wait, so the skeleton sidebar shows three groups of three rows whatever the role (the real one has 3, 6 or 12 items); the rail has no geometry that depends on the count.
8. **The static copy carries `hidden` and is shown only under `<html data-shell>` (plan review I1, I2).** The static root is `<div class="shell sk-shell" data-sidebar="expanded" hidden>`. With no stylesheet at all (the Vite dev server injects CSS from the module graph, a stale `index.html` whose hashed CSS 404s) the browser's `[hidden]` keeps it invisible instead of painting a 1424 px brand bolt; once `app.css` is in, the author rule `.shell { display: flex }` overrides the UA `[hidden]`, and `:root:not([data-shell]) .sk-shell[hidden] { display: none }` hides it on `/login`, `/setup` and when `theme-init.js` did not run. The React skeleton has no `hidden`, so no rule can hide it: a sign-in that finishes before the auth check (`LoginPage.submit` does not wait for the bootstrap) shows the skeleton, not a blank page. The parity test ignores `hidden` on the static root.
9. **One `TopProgress`, owned by `RequireAuth`.** `RequireAuth` returns `<><TopProgress />{body}</>` where `body` is the skeleton (with `<Pending />`), a `<Navigate>` or the children, so ONE bar instance (same DOM node) carries from the auth wait into `Layout`, which stops rendering it. The bar is not mounted on `/login` and `/setup`, as today. The store's own rules (120 ms show delay, 100 ms settle) keep the run going across the hand-over to the page's own loads.
10. **A parity test, not a generator (plan review M1).** `AppShellSkeleton.test.tsx` parses `index.html` with `new DOMParser().parseFromString(html, "text/html").getElementById("root")` and the output of `renderToStaticMarkup(<AppShellSkeleton sidebar="expanded" />)` into a `<template>`; it removes comment nodes and whitespace-only text nodes recursively and the `hidden` attribute on the static root, then asserts `expected.isEqualNode(actual)` (attribute order, `<path></path>` against `<path/>` and `data-x` against `data-x=""` do not matter); on a mismatch the message prints the generated markup to paste. Paste the copy with line breaks only between block elements (whitespace inside `.lbl > span > .sk-line` is inline). The build check (`grep` on `dist/index.html`) and the e2e (the HTML the server sends) prove the copy survives Vite and Caddy.
11. **Process.** The lighter process of W7f: ONE Opus plan review, Sonnet implementers (one per task, fresh), targeted tests per task, no per-task Opus review (no data, billing, migration; the auth code is not changed), then the controller's gates, ONE whole-wave Opus review in a real browser, ONE fix wave, one scoped re-review. No backend suite; `git diff main --stat -- backend` stays empty (the backend test `test_preferences_parity.py` reads `theme-init.js` and `index.html`, so it runs once after Task 3).
