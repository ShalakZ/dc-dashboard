# w26b: the figure ledger Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer brief says: "Edit files with the Edit tool or an anchored sed, never with a script that rewrites a whole file; after any scripted edit check the file's size and `git diff --stat`."

**Goal:** a month's figures are computed ahead of time by a background process, stored in the database, and read back instead of recomputed after an api restart, for a month nobody opened yet and for Check month - without ever serving a figure that w26's live path would not give.

**Architecture:** one table `figure_ledger` holds, per key of w26's figure cache (`month-days`, `window-values`) and per Check-month window (`month-check`), the very value the live path computes, as lossless JSON (zlib) plus the fingerprints it was made under. A new compose service `figures` (`python -m dcdash.figures`, same image) keeps the rows current. The api only reads: inside `figure_cache._run`, in the SAME repeatable-read snapshot that takes the config and data fingerprints, a stored row is used instead of running the engine when it is provably current (rules D3); otherwise w26's engine runs unchanged. Check month checks on the spot, every request.

**Tech Stack:** Python 3.12, SQLAlchemy async + asyncpg, Alembic, TimescaleDB, Docker Compose, pytest (Docker for DB tests).

**Brief:** `.waves/w26b.md` (R0-R9). **Ports:** `dcdash_e2e_w26b_vis` 18243/18597, `dcdash_e2e_w26b_look` 18244/18598 (both checked free with `ss -ltn` at 06:30).

## Facts checked in the merged w26 code (main 099bde2)
- `core/figures.py` builds two values in one repeatable-read snapshot through `figure_cache.get_or_compute(db, kind, start, end, params, make)`: `MonthDays` (kind `month-days`, window = the month in UTC, params `(tz_name,)`: per asset one Billing day entry per local day computed with `now=FAR_FUTURE`; `entries_at` masks the days after `now` per request) and `WindowValues` (kind `window-values`, window `[first,last)` = `widgets._hour_window`, params `(last_day, tz_name, cost)`). Consumers: Billing (`api/billing.py:70`), the comparison (`widgets.py:702-703`), plain/breakdown widgets (`widgets.py:579`), a closed month's `live`. All of them go through `month_days` / `window_values`: no consumer changes.
- `figure_cache._run` takes the config fingerprint (must equal `key[4]`), the data fingerprint and runs `compute(session)` in one snapshot; `_Entry` keeps `data_fp`, `checked_at`, `compute`; `_warm` re-runs `entry.compute`; `require_fresh` is a ContextVar.
- The data fingerprint (`_DATA`) hashes the rows `[start,end)`, each counter's baseline and each meter's first bucket. It covers the current partial hour too (`readings_1h` is a real-time aggregate), so an OPEN window's fingerprint moves with every collector flush.
- A day entry is `{"kwh": float, "cost": float|None, "estimated": bool, "partial": bool, "no_data": bool}`. `AssetTree` = `AssetNode(id, parent_id, name, sort_order)`; `TariffRow(asset_id|None, rate float, effective_from date)`; every datetime in the values is aware with `timezone.utc` (from the database and from `month_bounds` / `local_days`; the codec still tags the tzinfo kind, so any other kind is refused, never stored silently). `AssetTree.load` is `select(Asset)` with no ORDER BY (heap order); nothing iterates `tree.nodes` for output (grep: only indexing and `sorted(...)`), so the codec may store nodes sorted by id. The asset and fleet summary read one day and keep w26's path (brief R5's "asset summary" does not apply).
- `this_month`'s window is `[floor_hour(month start), ceil_hour(now))`: its key changes every hour; `last_month`'s is the whole previous month.
- Check month (`api/billing_check.py`) is uncached by w26 ruling I2; its report is `build_report(tree, inputs, start, stop, rate_for, zone, names)`; `names` only fill the `point`/`source` keys of the items of the nine groups in `THINGS` (`None` without names); `closed`, `state`, the envelope are per request. It reads the `before` bucket for EVERY point (the figure cache's fingerprint hashes baselines for counters only), so it needs a fingerprint of its own.
- `readings_1h` is a continuous aggregate with a 7-day refresh policy: an hour older than 7 days changes only through the seeder, a restore (replaces this table too), a migration or a hand-run refresh.
- Compose: the api runs `alembic upgrade head` and is the healthy gate; `update.ps1` runs `build api web` then `up -d` (starts every non-profile service, so `figures` starts without a script change); `restore.sh` and `restore.ps1` stop and start `api collector` only.
- `docs/dashboards-and-billing.md` is 74,996 of the 80,000 bytes `test_docs_links` allows: add under 3 KB there.

## Decisions (each a Ruling in the ledger; the plan review refines them)
- **D1 One table, one row per value** (not the brief's two tables with hourly arrays): w26 changed what is cached, a reader needs a whole window for every asset anyway, and one row is one atomic write ("a reader never sees half a month"). Primary key `(kind, start_ts, end_ts, params)`; no foreign key. Columns: `engine`, `config_fp`, `data_fp`, `snapshot_at` (database clock `now()` of the snapshot the value was made in), `checked_at` (database clock: the last snapshot in which the data fingerprint was seen equal to `data_fp`; `snapshot_at <= checked_at`), `size_bytes`, `payload bytea` with `STORAGE EXTERNAL` (already compressed), `params text` (not jsonb: jsonb would normalise and hide a difference). `end_ts` of a `month-check` row is the report's `stop` (review I8: an hour later is another key).
- **D2 Lossless codec, no pickle** (`core/ledger_codec.py`): canonical JSON (compact separators, ASCII), zlib. Types are kept exactly: float vs int, tuple vs list, int dict keys (stored as pairs), `-0.0`, NaN, the tzinfo kind, `fold`, key order inside a day entry and of the `entries` dict. Two things are put in a canonical ORDER because their live order is not stable (review I4): an `AssetTree`'s nodes sorted by id, a frozenset sorted. `canonical(value)` is the uncompressed JSON bytes. A stored row is equal to a live value when `canonical(decode(row))` equals `canonical(live)` (this also tests the decoder); before every write the worker checks `canonical(decode(payload)) == canonical(value)` and refuses a row that does not round-trip (review M7).
- **D3 When a row may be used** (inside `_run`, in the request's own repeatable-read snapshot, after the config fingerprint): the hook reads, in ONE statement inside a SAVEPOINT (`session.begin_nested()`, so a missing table or any SQL error leaves the snapshot usable, review I2), the row's header and the database `now()`. The row is a miss unless `engine` equals this build's `engine_id()`, `config_fp` equals the snapshot's, and `snapshot_at <= checked_at <= now()` (a row dated in the future, e.g. restored from a machine whose clock was ahead, never counts, review C1). Then: (b) if the window is OPEN (`end_ts` later than `now() - 7 days - 1 hour`: the current month, `this_month`, the previous month in its first week) AND `now() - checked_at <= 60 s` AND the request is not under `require_fresh` AND `checked_at` is not older than the `data_at` of the cache entry it would replace: the row is used WITHOUT reading the data fingerprint (review I5: that read is the cost to avoid), and the entry is stored with the ROW's `data_fp`, `data_at = checked_at` and a `checked_at` back-dated by the row's age but never by more than TTL - 5 s (so a stored entry is not born expired; the cache's own revalidation then sees the difference and the next request or keep-warm takes a newer row or runs the engine). Otherwise the data fingerprint is read as w26 does and (a) a row whose `data_fp` equals it is used (EXACT: the only rule for a SETTLED window and under `require_fresh`; `data_at = now()` of the snapshot); anything else is a miss and the engine runs unchanged (and a row older than the entry it would replace is a miss, never an older figure). `_Entry` gets `data_at` (database `now()` of the data the value reflects; `None` when the ledger is not consulted) and `_put` refuses a replacement whose `data_at` is older than the stored entry's, as well as the stamp rule (review I1). The hook never raises: SQL errors, `zlib.error`, `ValueError`, `KeyError`, `TypeError`, `UnicodeError`, a decoded value whose `config_fp` differs from the row's, are a miss, logged once per kind. `fresh` is passed to `_run` as an argument, not read from the ContextVar (review M5). Decompress and decode run on the compute thread (`compute.run`), never on the event loop (review I3). A figure may move back by up to 60 s after an api restart or an LRU eviction (R8 accepts it; docs "Limits"). The cache's TTL logic, coalescing, keep-warm and snapshot consistency (w26 C2) are untouched.
- **D4 Engine id** = first 16 hex of sha256 over every `*.py` under `dcdash/core` and `dcdash/figures` plus `dcdash/api/billing_check.py` (names and bytes, sorted), `sys.version` (the full string), the `tzdata` package version if importable (else `none`) and `LEDGER_FORMAT = 1`, computed once. An image built from other code, another Python or other zone rules never matches old rows.
- **D5 The worker** (`dcdash/figures/`): one process, one asyncio loop. One advisory lock on a DEDICATED connection (NullPool, a two-int key in its own namespace as `api/sources.py:26` does), checked every cycle; a worker that has lost it stops writing and tries again; an idle standby still beats the heartbeat. The upsert is `ON CONFLICT (pk) DO UPDATE ... WHERE figure_ledger.snapshot_at < EXCLUDED.snapshot_at OR figure_ledger.snapshot_at > now()`, and the worker deletes rows dated in the future, so no writer rolls a row back and a bad clock heals (review C1). Every `DCDASH_FIGURES_INTERVAL` seconds (30) it lists its targets, newest first: `month-days` for the site zone for the current month and the previous `DCDASH_FIGURES_MONTHS - 1` (6); `window-values` (energy and cost) for `this_month` (the window a request made now would ask for, derived from `resolve_range` and `_hour_window`, never copied) and `last_month`; `month-check` for each of those months with key `(start, stop)` (an open month's stop is the current hour; none when stop <= start). A site zone that is unknown or fails `validate_whole_hour_zone` has no targets and one log line per change (review M12). **Label and value come from ONE repeatable-read transaction** (review C2: the same rule as `figure_cache._run`): config fingerprint, data fingerprint, `now()` and the value are all read inside it, `snapshot_at = now()`, and a write asserts `value.config_fp == label config_fp` (MonthDays and WindowValues carry it). A target is looked at in such a snapshot first; if the stored row has the same engine, config and data fingerprints the worker runs `UPDATE ... SET checked_at = GREATEST(checked_at, now()) WHERE pk AND engine = :e AND config_fp = :c AND data_fp = :d` inside the same transaction (review M2); otherwise it recomputes with the SAME builders the cache uses (extracted from `figures.py`) and upserts, and when the new payload bytes equal the stored ones it touches instead (review M11). A config change makes every target due at once; settled targets are looked at every 10 minutes, open ones every cycle. Rows that are no longer targets are deleted. Errors never stop the loop (log, back off, reconnect; a missing table is the same: back off and retry). SIGTERM ends it between targets. The heartbeat file is touched after every cycle (its healthcheck limit exceeds the longest cycle).
- **D6 Check month**: the key is `('month-check', start, stop, (tz_name,))` and the fingerprint covers `[start, stop)`: the request takes the config fingerprint, a Check-month data fingerprint (SQL hash over the rows of `billing_check._ROWS`: row, before for every point, first) and ONE statement that returns the row's header and payload; it uses the row only when engine, config and data all equal and the `snapshot_at <= now()` guard holds (always exact, no 60 s rule: only complete hours are in `[start, stop)`). The three reads run on the request's session (a row that equals both fingerprints is the report of a state that existed; header and payload are one statement). Names are patched in place into the `point`/`source` keys. On any miss, or any error, the endpoint runs today's code unchanged. Task 0 measures the Check-month fingerprint at 370 assets; if the fingerprint alone is over about 150 ms the 300 ms Check-month target is reported as missed, honestly.
- **D7 `python -m dcdash.figures.rebuild`**: `--check` recomputes each stored row in one snapshot (as D5) and prints one line per row: `equal` (same data fingerprint and `canonical(decode(row)) == canonical(live)`), `moved on` (the data changed since the row was made: not a difference), `stale` (other engine or config), `DIFFERENT` with the first differing asset and day; a summary with the four counts (an open month is normally `moved on`, so it is never a silent all-clear); exit 1 on any `DIFFERENT`; writes nothing. `--all` = the worker's target list; `--month YYYY-MM` = the targets of that month and is refused (exit 2, a message) for a month outside the target list, because the worker would delete what it wrote (review I9). The nightly self-check (03:00 site time, once per local day) runs the same comparison over every stored row; a `DIFFERENT` writes a journal event (component `figures`, kind `figures.mismatch`) and deletes that row.
- **D8 Switches**: `DCDASH_FIGURE_LEDGER=0` makes readers ignore the table and the worker idle (used by the corpus "ledger off" pass). The compose file passes `DCDASH_FIGURE_LEDGER`, `DCDASH_FIGURES_INTERVAL` and `DCDASH_FIGURES_MONTHS` (`${VAR:-}` style) through `x-backend-env`, and the `figures` service uses `environment: *backend-env` (without it the zone defaults differ, review M8).
- **D9 Scripts and docs**: `restore.sh` and `restore.ps1` stop and start `figures` with `api collector` (a worker must not compute from a half-restored database; the tests assert the new needles explicitly, and `restore.ps1` must not treat a missing `figures` container as a failed restore, review M10); `update.ps1` is not changed (`up -d` starts the service; `$script:Services` does not check it: documented in `upgrading.md` and `field-debugging.md`, review M9); the ledger stays in the backup (the dump is consistent; the fingerprints and the future-date guard reject any mismatch). `scripts/scratch.override.yaml` and the drill overrides give `figures` its own scratch image tag, and a compose test pins that every service built from `./backend` is in `scratch.override.yaml` (review I6). No new section in the diagnostics report: events use the existing journal (T6 checks the report lists them).
- **D10 Numpy and compiled code stay out (R9).** Rung 4 is looked at only if the profile shows an interpreter loop over 50 ms after the ledger.
