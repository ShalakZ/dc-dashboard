# w26b: the figure ledger Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every implementer brief says: "Edit files with the Edit tool or an anchored sed, never with a script that rewrites a whole file; after any scripted edit check the file's size and `git diff --stat`."

**Goal:** a month's figures are computed ahead of time by a background process, stored in the database, and read back instead of recomputed after an api restart, for a month nobody opened yet and for Check month - without ever serving a figure that w26's live path would not give.

**Architecture:** one table `figure_ledger` holds, per key of w26's figure cache (`month-days`, `window-values`) and per Check-month window (`month-check`), the very value the live path computes, as lossless JSON (zlib) plus the fingerprints it was made under. A new compose service `figures` (`python -m dcdash.figures`, same image) keeps the rows current. The api only reads: inside `figure_cache._run`, in the SAME repeatable-read snapshot that takes the config and data fingerprints, a stored row is used instead of running the engine when it is provably current (rules D3); otherwise w26's engine runs unchanged. Check month checks on the spot, every request.

**Tech Stack:** Python 3.12, SQLAlchemy async + asyncpg, Alembic, TimescaleDB, Docker Compose, pytest (Docker for DB tests).

**Brief:** `.waves/w26b.md` (R0-R9). **Ports:** `dcdash_e2e_w26b_vis` 18243/18597, `dcdash_e2e_w26b_look` 18244/18598 (both checked free with `ss -ltn` at 06:30).

## Facts checked in the merged w26 code (main 099bde2)
- `core/figures.py` builds two values in one repeatable-read snapshot through `figure_cache.get_or_compute(db, kind, start, end, params, make)`: `MonthDays` (kind `month-days`, window = the month in UTC, params `(tz_name,)`: per asset one Billing day entry per local day computed with `now=FAR_FUTURE`; `entries_at` masks the days after `now` per request) and `WindowValues` (kind `window-values`, window `[first,last)` = `widgets._hour_window`, params `(last_day, tz_name, cost)`). Consumers: Billing (`api/billing.py:70`), the comparison (`widgets.py:702-703`), plain/breakdown widgets (`widgets.py:579`), a closed month's `live`. All of them go through `month_days` / `window_values`: no consumer changes.
- `figure_cache._run` takes the config fingerprint (must equal `key[4]`), the data fingerprint and runs `compute(session)` in one snapshot; `_Entry` keeps `data_fp`, `checked_at`, `compute`; `_warm` re-runs `entry.compute`; `require_fresh` is a ContextVar.
- The data fingerprint (`_DATA`) hashes the rows `[start,end)`, each counter's baseline and each meter's first bucket. It covers the current partial hour too (`readings_1h` is a real-time aggregate), so an OPEN window's fingerprint moves with every collector flush.
- A day entry is `{"kwh": float, "cost": float|None, "estimated": bool, "partial": bool, "no_data": bool}`. `AssetTree` = `AssetNode(id, parent_id, name, sort_order)`; `TariffRow(asset_id|None, rate float, effective_from date)`; datetimes are aware (`timezone.utc` from the database, `ZoneInfo` from `month_bounds`/`local_days`).
- `this_month`'s window is `[floor_hour(month start), ceil_hour(now))`: its key changes every hour; `last_month`'s is the whole previous month.
- Check month (`api/billing_check.py`) is uncached by w26 ruling I2; its report is `build_report(tree, inputs, start, stop, rate_for, zone, names)`; `names` only fill the `point`/`source` keys of the items of the nine groups in `THINGS` (`None` without names); `closed`, `state`, the envelope are per request. It reads the `before` bucket for EVERY point (the figure cache's fingerprint hashes baselines for counters only), so it needs a fingerprint of its own.
- `readings_1h` is a continuous aggregate with a 7-day refresh policy: an hour older than 7 days changes only through the seeder, a restore (replaces this table too), a migration or a hand-run refresh.
- Compose: the api runs `alembic upgrade head` and is the healthy gate; `update.ps1` runs `build api web` then `up -d` (starts every non-profile service, so `figures` starts without a script change); `restore.sh` and `restore.ps1` stop and start `api collector` only.
- `docs/dashboards-and-billing.md` is 74,996 of the 80,000 bytes `test_docs_links` allows: add under 3 KB there.

## Decisions (each a Ruling in the ledger; the plan review refines them)
- **D1 One table, one row per value** (not the brief's two tables with hourly arrays): w26 changed what is cached, a reader needs a whole window for every asset anyway, and one row is one atomic write ("a reader never sees half a month"). Primary key `(kind, start_ts, end_ts, params)`; no foreign key. Columns: `engine`, `config_fp`, `data_fp`, `snapshot_at` (database clock, start of the snapshot the value was made in), `checked_at` (database clock, last time the data fingerprint was seen equal to `data_fp`), `size_bytes`, `payload bytea`.
- **D2 Lossless codec, no pickle** (`core/ledger_codec.py`): canonical JSON (no key sorting, compact separators, ASCII), zlib. Types are kept exactly: float vs int, tuple vs list, int dict keys (stored as pairs, order kept), `-0.0`, NaN, the tzinfo kind (`timezone.utc` vs `ZoneInfo(key)`), `fold`, key order inside a day entry. The proof of equality between a stored row and a live value is byte equality of the canonical JSON of both (injective on these types).
- **D3 When a row may be used** (inside `_run`, same snapshot): `engine` equals this build's `engine_id()` AND `config_fp` equals the snapshot's AND either (a) `data_fp` equals the snapshot's data fingerprint (EXACT: always allowed, the only rule under `require_fresh`), or (b) the window is OPEN (`end_ts` later than `db_now - 7 days - 1 hour`, so the current month, `this_month`, and the previous month in its first week) AND `db_now - checked_at <= 60 s` AND the row's `snapshot_at` is not older than the stored cache entry it would replace (a figure never goes back in time). In case (b) the entry is stored in the cache with the ROW's `data_fp` and a `checked_at` back-dated by the row's age, so the cache's own revalidation sees the difference and the next request or keep-warm takes a newer row or runs the engine. A SETTLED window has only rule (a): a seed, a hand-run refresh or late rows are seen at once. The cache's TTL logic, coalescing, keep-warm, snapshot consistency (w26 C2) are untouched.
- **D4 Engine id** = first 16 hex of sha256 over every `*.py` under `dcdash/core` and `dcdash/figures` plus `dcdash/api/billing_check.py` (names and bytes, sorted), `sys.version_info[:2]` and `LEDGER_FORMAT = 1`, computed once. An image built from other code or another Python never matches old rows.
- **D5 The worker** (`dcdash/figures/`): one process, one asyncio loop, one advisory lock (`pg_try_advisory_lock`) so a second instance idles and takes over when the first dies; the upsert is `ON CONFLICT ... DO UPDATE ... WHERE figure_ledger.snapshot_at < EXCLUDED.snapshot_at` so no writer rolls a row back. Every `DCDASH_FIGURES_INTERVAL` seconds (30) it lists its targets, newest first: `month-days` for the site zone for the current month and the previous `DCDASH_FIGURES_MONTHS - 1` (6); `window-values` (energy and cost) for `this_month` (the window a request made now would ask for, derived from `resolve_range` and `_hour_window`, never copied) and `last_month`; `month-check` for each of those months (an open month's stop is the current hour). For each target one snapshot reads the config and data fingerprints: equal to the stored row (and same engine) means `UPDATE checked_at = now()`; otherwise it recomputes with the SAME builder functions the cache uses (extracted from `figures.py`, one source of truth) and upserts in one statement. A config change makes every target due at once; settled targets are looked at every 10 minutes, open ones every cycle. Rows that are no longer targets are deleted. Errors never stop the loop (log, back off, reconnect). SIGTERM ends it between targets. A heartbeat file is touched after every cycle and is the container's healthcheck.
- **D6 Check month**: the request takes the config fingerprint, a Check-month data fingerprint (SQL hash over the rows of `billing_check._ROWS`: row, before for every point, first), and ONE statement that returns the row's header and payload; it uses the row only when engine, config and data all equal (always exact, no 60 s rule: only complete hours are in `[start, stop)`, so the fingerprint is stable within an hour). Names are patched in place into the `point`/`source` keys. On any miss the endpoint runs today's code unchanged.
- **D7 `python -m dcdash.figures.rebuild`**: `--check` recomputes each stored row in one snapshot and compares the canonical bytes with the row when the snapshot's data fingerprint equals the row's (otherwise it says `moved on`, not a difference), one line per row, exit 1 on any difference, writes nothing; `--month YYYY-MM` / `--all` rebuild. The nightly self-check (03:00 site time, once per local day) is the same comparison over every stored row; a difference writes a journal event (component `figures`) and deletes that row.
- **D8 Switches**: `DCDASH_FIGURE_LEDGER=0` makes readers ignore the table and the worker idle (used by the corpus "ledger off" pass).
- **D9 Scripts and docs**: `restore.sh` and `restore.ps1` stop and start `figures` with `api collector` (a worker must not compute from a half-restored database); `update.ps1` is not changed (`up -d` starts the service; the service is optional); the ledger stays in the backup (the dump is consistent; fingerprints reject any mismatch). No new section in the diagnostics report: events use the existing journal (T6 checks the report lists them).
- **D10 Numpy and compiled code stay out (R9).** Rung 4 is looked at only if the profile shows an interpreter loop over 50 ms after the ledger.

## Review focus
1. A row is never used unless config and engine match, and (settled) data matches: change a rate, flip sibling order, map a meter, seed an old month, late rows in last week, move the zone.
2. An open-window row is never older than 60 s and never older than the entry it replaces; `require_fresh` never takes a mismatching row.
3. The codec loses nothing: types, order, tzinfo, -0.0.
4. Two workers, a restart of the database, a restore, SIGTERM: no half or rolled-back row, no stall of api or collector.
5. Check month: names, key order, `closed`, not-begun, first hour.
6. The migration: values before and after, lossless downgrade.
