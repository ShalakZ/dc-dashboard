## Facts checked in the code (LESSONS A12: the brief is not law)

- `STARTER_PACK` (`backend/dcdash/core/asset_kinds.py:25`) has 39 `(name, icon)` entries; the 16 "Common" names of the brief are all in it and keep its relative order. Migration 0010 seeds the ten `STARTERS = ("Site", "Building", "Room", "Row", "Rack", "Panel", "Meter", "Circuit", "Other equipment", "generic")` (migration file line 56), "for every key no asset uses"; the registry row carries the spelling the assets used, so the Starter test is by KEY (`kind_key`), never by name.
- `GET /api/asset-kinds` returns `KindOut {id, name, icon, asset_count}` sorted by key (`api/asset_kinds.py::list_kinds`); `create_kind` and `update_kind` build their answer with the same `as_row`, so one change covers all three. `POST /api/asset-kinds/starter-pack` takes no body and returns `StarterOut {added, already_there}`; `already_there = len(STARTER_PACK) - len(added)`; one `kind.starter_pack_added` audit row `{count, names}` only when something was added.
- `DELETE /api/asset-kinds/{id}?move_to=&expect_assets=`: a kind in use needs `move_to` (else 409 with `assets`), `expect_assets` is checked only on a move (409 `{detail, assets}`), `move_to == id` is 422, a gone target 422 "That kind no longer exists.", a gone kind 404. One audit row per delete with `moved_to` and `assets`. Each call is its own transaction; the server needs no change for a client loop.
- The jump to the top: `AssetKindsPage.tsx:135-137` focuses New kind (`newKindButton.current ?? heading.current`) after a confirmed delete. The Haiku sweep of every `.focus(` call (the controller's own, summarised here) found the same pattern, no `preventScroll`, in `pages/UsersPage.tsx:21` (heading after a user delete) and `components/RolesPanel.tsx:71` (New role button after a role delete). Shared dialogs return focus to the opener (`ConfirmDeleteDialog.tsx:64`, `Modal.tsx:54`, `useDialogFocus.ts:51`): the opener is on screen, so they cannot jump; they are left alone (Ruling 12c).
- `lib/treeSelect.ts` (W7p) already has the pure reducers over `PickState {ids, anchor}`: `toggle`, `pickRange(state, order, id)` (replaces the picks with the anchor-to-id range in `order`), `clear`, `prune`, `unpick`, `EMPTY_PICK`. They are id-number based and know nothing about trees except `visibleOrder`, which this page does not use. Reuse them; add only `pickAll`/`pickUnused` in the new `lib/kindsView.ts`.
- Existing look to reuse: the outlined neutral tag `.role-badge` (`styles/pages-admin.css:93`, "Built in") and the segmented control `.seg-switch` with `aria-pressed` buttons (`pages-admin.css:152`, used by the Audit page). ## Decisions taken here (the brief stands; these refine it; the owner may overrule any)

1. **Process and order.** Plan -> ONE Opus plan review (report `plan-review-report.md`, folded in: see F3 for the waves, which override this line: S0 scaffold + T1, then T2 + T3a + T3c, then T3b, then T4). The full backend suite is started detached as soon as T1 is committed and the tree has no backend edit in flight (the front-end tasks do not touch `backend/`); it is rerun only if a later task changes `backend/`.
2. **Starter is the server's word.** `KindOut.starter: bool` = `kind_key(name) in STARTER_KEYS`, where `STARTER_KEYS = {kind_key(n) for n in SEEDED_STARTERS} | {kind_key(n) for n, _ in STARTER_PACK}` (49 keys). `SEEDED_STARTERS` is the ten names as a constant next to `STARTER_PACK`; a test imports the migration module and asserts the tuple equals its `STARTERS`. The flag follows the CURRENT key: renaming a starter kind to something else clears it, naming a custom kind "UPS" sets it. No copy of the lists in TypeScript, no parity file.
3. **The Common list.** `COMMON_NAMES: tuple[str, ...]` = UPS, Battery, PDU, RPP, ATS, STS, Switchgear, Transformer, Generator, Chiller, CRAC, Cooling tower, Server, Network switch, Sensor, Fire suppression (16, the supervising session's choice; the owner can edit the tuple in review). `COMMON_PACK` = the `STARTER_PACK` entries whose name is in it, in pack order. `POST /api/asset-kinds/starter-pack?set=common|all` (Query alias `set`, `Literal["common", "all"]`, default `common`; anything else is the automatic 422). `StarterOut.already_there = len(chosen pack) - len(added)`. Same permission (`assets.kinds`), same idempotence (ON CONFLICT DO NOTHING by key), same audit event and detail `{count, names}` (the names say what was added; no `set` key, so the frozen audit-text tests and `auditText.ts` stay untouched). No change to `ROUTE_PERMISSIONS`, the coverage gate or the matrix.
4. **The page, top to bottom.** Header (title, crumbs, actions) -> optional `kinds-note` (a reader) -> **toolbar row** -> table. Header actions for `assets.kinds`: `Add common data-centre kinds` (plain button, replaces `Add data-centre kinds`), `New kind` (primary). Toolbar row (drawn once there are kinds; the skeleton draws a placeholder of the same height): left the filter, right ONE fixed slot. The slot holds, for `assets.kinds` holders only: nothing picked -> a quiet text button `Add all 39 data-centre kinds` (aria-disabled while pending); something picked -> the bar `12 selected` + `Select all unused` + `Delete` + `Clear`. The slot has a fixed flex-basis and min-height, so picking never moves the table (e2e: the table's top y is equal before and after the first tick, at 1440 and 1024). A reader's slot is empty.
5. **Filters.** A `role="group" aria-label="Show"` of four `aria-pressed` buttons, names `All 51`, `Starter 49`, `Yours 2`, `Unused 40` (the count is part of the name). Counts are over the whole list, not the picks. Yours = not starter; Unused = `asset_count === 0`. View state only (no URL, Ruling 12a). Choosing a filter clears the picks (a pick can never hide in a filtered-out row and then be deleted). A filter with no rows shows a muted line "No kinds match this filter." inside the table area; the toolbar stays. A kind that stops matching after a refetch (it was renamed, got an asset) simply leaves the list; picks are derived as `picks ∩ shown rows`, pruned in an effect.
6. **The Starter tag.** `<span className="kind-starter">Starter</span>` after the label, OUTSIDE `.kind-label` (the e2e lookups match `.kind-label` as a whole text: w7m `kindRow`, w7o `kindRow`). Outlined neutral tag like `.role-badge`: `--text-2` on the row background, 1px `--border-strong`, `--radius-sm`, never a pill. Contrast is tested in every preset and both modes (the css test pattern of `styles/asset-move.css.test.ts`). No colour token is added (LESSONS A10 not triggered).
7. **Selection** (needs `assets.kinds`; without it no checkbox column at all). Column 1 of the table: header checkbox `aria-label="Select all shown kinds"` (checked when every shown row is picked, `indeterminate` through a ref when some are; clicking it picks all shown rows, or clears when all are picked), row checkbox `aria-label="Select <name>"` (plain click toggles, Shift-click ADDS the range in shown order, see F6; Space on the focused checkbox is the native toggle). `tr` gets `data-kind-id` and the class `is-picked` (a tint token that exists; no new token). `Select all unused` picks every SHOWN row with `asset_count === 0`. Escape clears the picks, but only when nothing else is open: it is handled on the page root with a guard `!event.defaultPrevented`, no dialog (`dialog`, `deleting`, bulk) and no open row menu (LESSONS A8: innermost layer first; test: with a row menu open Escape closes the menu and the picks stay). ONE announcer: the `12 selected` text sits in a role-less `<span aria-live="polite" aria-atomic="true">` that is mounted from the start of the slot, no `role="status"` anywhere (LESSONS A9; the specs count `getByRole("status")`).
8. **Bulk delete = the existing route in a client loop** (the brief's default; no batch route, so no permission-matrix or coverage-gate change). New hook `useBulkDeleteAssetKinds()` in `api/queries.ts`: `mutateAsync({ items: {id, name, assetCount}[], moveTo: number | null })` deletes ONE AT A TIME, in list order, each `api.del("/api/asset-kinds/{id}" + ("?move_to=T&expect_assets=N" if the kind is in use, else no query))`, catching each error into `failed: {id, name, reason}[]` (reason = the server's detail with a capital, via `upperFirst`; a 409 turns into the server's own "N assets use this kind now..." sentence), and invalidates the same three keys ONCE in `onSettled`. It returns `{ deleted: number[], failed: [...] }`. A target that vanishes mid-loop makes the rest fail with the 422 sentence (no assets are lost: a move is atomic with its delete in one transaction on the server).
9. **The bulk dialog** (`components/BulkDeleteKindsDialog.tsx`, wraps `ConfirmDeleteDialog`; the single-kind `DeleteKindDialog` and the row menu stay exactly as they are). Title `Delete 12 kinds?` (one pick opens the same dialog, `Delete 1 kind?`). Message: none in use -> the first 8 names, comma separated, then ` and 4 more` when there are more, then ` Assets that carry these names later get an automatic icon.` Some in use -> `3 of these kinds are used by 7 assets. Move those assets to another kind, then delete the 12.` and the labelled select `Move the assets to` (children slot) listing every kind NOT in the selection, sorted by key, `Choose a kind…` first, Delete off until one is chosen (`confirmDisabled`). If no kind outside the selection exists and some are in use -> `blocked` (the dialog says why: `Every kind is selected, and 7 assets use some of them. Keep at least one kind to move them to.`). `onConfirm` runs the hook; if EVERY deletion failed it throws `Error(first reason)` (the dialog stays open and shows it; the list has refetched, the counts in the message follow); otherwise it resolves, the page closes the dialog, and the result is a toast: all gone -> `Deleted 12 kinds` (`Deleted 12 kinds, 7 assets moved to UPS` when assets moved); some failed -> an ERROR toast `Deleted 11 kinds. 1 could not be deleted: <first reason>` (`2 could not be deleted` for more; the first reason is shown). The deleted ids leave the picks (`unpick`); the failed stay picked. Counting sentence helpers live in `lib/kindsBulk.ts` with their own table test.
10. **Focus and scroll (Q6).** Every focus move this page makes after a change passes `{ preventScroll: true }`. After a single delete from the row menu: focus goes to the actions button of the next SHOWN row, else the previous one (found by `tr[data-kind-id]` in a ref'd table, the neighbour computed from the shown order at the moment Delete was chosen), else the active filter button, never `<body>`, never New kind. After a bulk delete: the active filter button. The unit test spies `HTMLElement.prototype.focus` and asserts the option; the e2e measures `window.scrollY` (and the scroll container's `scrollTop` if the layout scrolls inside one) before and after, 1 px tolerance. `UsersPage.tsx:21` and `RolesPanel.tsx:71` get the same `preventScroll` (Task 3c) with a unit assertion each.
11. **Pack copy.** Toasts: `Added N kinds` / `Added 1 kind` as today; nothing to add -> `All the common data-centre kinds are already there` (common) or `All the data-centre kinds are already there` (all, the old sentence). The page asks `POST .../starter-pack?set=common|all` through `useAddStarterKinds()` -> `mutateAsync("common" | "all")`; the param is sent for `all` only (`set=all`), common is the server default. `already_there` is not shown anywhere. The InfoTip in the header's sub-line is unchanged.
12. **Rulings (also in the ledger).** (a) The filter is not in the URL (cheap to add, but the page has no other URL state and a stale `?show=unused` link would hide kinds for a reader; cost if wrong: the owner wants a bookmark). (b) Bulk delete is a client loop, not a batch route (cost: 12 requests; each keeps its own audit row and its own stale guard; a batch route would add a permission-matrix row and a transaction test for no user-visible gain). (c) The shared dialogs that return focus to their opener are left alone (the opener is on screen, cannot jump). (d) Starter follows the current key. (e) The audit detail does not gain `set`. (f) `Select all unused` works on the shown rows. (g) "Add all 39" carries the number as a literal in the label; the e2e and the backend test both pin 39, so a pack change fails a test, not a user.
