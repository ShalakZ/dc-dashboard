# w28 Display links, playlists and the Displays page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An administrator makes a playlist of dashboards and a display with a secret link; a browser that opens the link is a connected display (no sign-in) that can read only that playlist; the link can be revoked at once. The rotating wall screen is w29.

**Architecture:** Three new tables (migration `0015`); one credential (a 256-bit secret, only its SHA-256 stored, carried in a cookie scoped to `/api/display`); three display routes under `/api/display` that never become a user session; admin routes behind the 32nd permission `displays.manage`; a Displays page; a minimal `/display` page mounted OUTSIDE the auth providers.

**Tech Stack:** FastAPI + SQLAlchemy async + Alembic + pytest (testcontainers) / React 19 + React Router + TanStack Query + Vitest / Playwright.

**Spec:** `.waves/w28.md` (the brief, rulings R1 to R13, which this plan refines and corrects) and `.superpowers/sdd/power-dashboard-and-display/DESIGN.md` section 5.7. Tier L (Ruling in the ledger).

## Decisions that refine the brief (each is also a `Ruling:` in the ledger)
1. **R5' limiter** as above.
2. **Stable item ids.** `PUT /api/playlists/{id}` items carry an optional `id`: a matching id of THIS playlist is updated in place (position and seconds and dashboard and focus), a missing one is deleted, an item without `id` is inserted. A display that holds an item id (w29 posts `{item, widget}`) therefore keeps working across a save. An `id` of another playlist is 422. No UNIQUE on position; the order is `(position, id)`.
3. **`display.connected` is throttled** by a `RowBudget(30, 300)` so a kiosk that reloads in a loop cannot flood the audit table; `last_seen_at`/`last_client` are written by the playlist route with a conditional update that skips a write when the stored time is under 50 seconds old (a 60-second poll then always writes).
4. **Origin/CSRF for the claim** (R5): the request needs `Content-Type: application/json`; refuse (403) a `Sec-Fetch-Site` of `cross-site` or `same-site`; refuse (403) a present `Origin` whose host:port differs from the `Host` header. Absent headers (curl, tests, old browsers) pass; the secret is the credential, these only stop a hostile page from enrolling a visitor's browser.
5. **Shared compute.** `api/widget_data.py` gets `async def compute_checked(body: WidgetDataRequest, db) -> WidgetResult` (text -> 422, validate, comparison/range rule, `compute_widget` with `_now()`); `_compute` keeps the focus gate then calls it; the display route builds a `WidgetDataRequest` from stored values and calls it. One function, so the two answers cannot drift and tests that patch `widget_data._now` cover both.
6. **`api/health.py`** gets `async def read_live_status(db) -> LiveStatus` used by `live_status` and the display playlist.
7. **Per-display limit** 120 widget-data requests a minute: one `RowBudget(120, 60)` per display id in a dict (at most 50 displays), 429 + `Retry-After: 60` when over.
8. **Skip rule order** (core): `dashboard_id IS NULL` -> `dashboard_deleted`; else a `focus_asset_id` not in the asset tree -> `focus_gone`; else the dashboard has no widgets -> `no_widgets`; else none. A skipped item still returns what exists (`dashboard` with its widgets when present), and `dashboard`/`focus` are `null` where nothing exists.
9. **`no-store`.** The claim, create, playlist and widget-data answers carry `Cache-Control: no-store`.
10. **Mutation hygiene (front end).** The create-display mutation uses `gcTime: 0`; on Done/close the page calls `reset()` and drops the secret from component state; a unit test asserts the secret is in neither the mutation cache, the query cache nor the DOM after Done.
11. **Nav order.** Administer: Users & Roles, Settings, Tariffs, Storage, **Displays**, Audit, Diagnostics (icon: an inline SVG screen). `PAGE_NEED.displays = ["displays.manage", "dashboards.view"]`.
12. A non-admin custom role may be granted `displays.manage` (it is not in `NOT_FOR_CUSTOM_ROLES`), so the custom-role count rises 30 -> 31 everywhere it is pinned.

## API contract (T3/T4 implement it; T6/T7 consume it; w29 builds only on the display half)
Admin, every route gated first by `require_permission("displays.manage")`, in `ROUTE_PERMISSIONS`:
- `GET /api/displays` -> `{displays: [{id, name, playlist_id, playlist_name, status: "active"|"revoked", created_at, last_seen_at|null, last_client|null, revoked_at|null}], playlists: [{id, name, item_count, skipped_count, display_count, items: [{id, position, seconds, dashboard_id|null, dashboard_name|null, focus_asset_id|null, focus_name|null, skipped: null|"dashboard_deleted"|"focus_gone"|"no_widgets"}]}], limits: {displays: 50, playlists: 30, items: 20, min_seconds: 10, max_seconds: 3600}}`. Never a secret or a hash (the response models have no such field). `dashboard_name`/`focus_name` are the live name, or the stored snapshot when the thing is gone.
- `POST /api/playlists` and `PUT /api/playlists/{id}` body `{name, items: [{id?, dashboard_id, focus_asset_id?, seconds}]}` (name stripped, 1 to 100, unique, 409 "a playlist with this name already exists"; 0 to 20 items, 422 over; `seconds` 10 to 3600; the dashboard must exist (422); a focus must exist in the tree (422) and needs `user.can("assets.view")` (403)); answer one playlist object as above. 30 playlists max (422), under an advisory lock like the dashboard cap. Snapshots (`dashboard_name`, `focus_name`) are written at save.
- `DELETE /api/playlists/{id}` 204; 409 `{"detail": "this playlist is shown by: Hall TV, Wall B"}` when a display uses it (also on the FK violation).
- `POST /api/displays` `{name, playlist_id}` -> 201 `{display: <display object>, link_secret: "<43 chars>"}` + `no-store`. 50 displays max (422). `PUT /api/displays/{id}` `{name?, playlist_id?}` (at least one) -> the display object. `POST /api/displays/{id}/revoke` -> the display object (idempotent: no second audit row). `DELETE /api/displays/{id}` -> 204.

Display (`current_display`, cookie `dcdash_display`), R6 exactly, with these shapes:
- `POST /api/display/claim` `{secret}` -> 204 + Set-Cookie (`HttpOnly; SameSite=Strict; Path=/api/display; Max-Age=34560000`; `Secure` when `_is_https`) + `no-store`; 401 `{"detail": "this display link is not valid"}` (one text for wrong, revoked, deleted); 403 (origin rules); 422 (not JSON / bad shape); 429 + `Retry-After` when the address is blocked.
- `GET /api/display/playlist` -> `{display: {name}, playlist: {name, items: [{id, seconds, dashboard: {id, name, range, widgets: [{id, type, title, config, x, y, w, h}]}|null, focus: {id, name, trail: [str]}|null, skipped}]}, site: {name, timezone}, build, status: <LiveStatus>}`. `site.name` is the Settings site name (find the setting `/api/site` family uses; if the site has no name field use the app title "DC Dashboard" and say so in the code comment).
- `POST /api/display/widget-data` `{item, widget}` (ints, `extra="forbid"`) -> the same body as `/api/widget-data` for the stored config; 404 `{"detail": "not found"}` for an item not in THIS display's playlist, a widget not on that item's dashboard, or an item whose dashboard is gone; 422 for a text widget; 429.
- Any other route with only the display cookie: 401, exactly as without it.
