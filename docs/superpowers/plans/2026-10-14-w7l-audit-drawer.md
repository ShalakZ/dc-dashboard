## Shared contracts (Tasks 1, 2, 3, 4 build against these; they run in parallel)
**Backend `refs`** (Task 1 produces, Task 2 consumes). Every audit item (list items and the single entry) gains `"refs"`, ALWAYS present, `{}` when empty:
```json
{"id": 12, "action": "tariff.created", "detail": {"asset_id": 5, "...": "..."}, "refs": {"asset": {"5": "MV2-R1-LV-Panel-02"}}}
```
Kinds: `asset`, `user`, `source`, `dashboard`, `point` (names from `assets.name`, `users.username`, `sources.name`, `dashboards.name`, `points.name`). A kind appears only when at least one of the entry's ids of that kind still exists; inside it only the ids that exist (string keys). An id that is not there is a deleted target.
Ids are read from the entry's `detail` AND, when they are objects, from `detail.before` and `detail.after`, by these keys: `asset_id`→asset, `parent_id`→asset, `user_id`→user, `source_id`→source, `dashboard_id`→dashboard, `point_id`→point. Accept an id only if `type(v) is int` (not `bool`), `0 < v <= 2_147_483_647` (stored JSON is arbitrary; an out-of-range number must never reach the `IN` query). One `SELECT id, name ... WHERE id IN (...)` per kind that has ids, for the whole page (never per row); no query for a kind with no ids.
**Frontend types** (Task 2 adds to `frontend/src/api/types.ts`; Tasks 3-5 import):
```ts
export type RefKind = "asset" | "user" | "source" | "dashboard" | "point";
export type AuditRefs = Partial<Record<RefKind, Record<string, string>>>;
// AuditEntry gains:  refs?: AuditRefs   // optional only so test fixtures stay small: undefined = "no lookup was made"
export function describeAudit(entry: AuditEntry): AuditView   // unchanged signature; reads entry.refs
```
`AuditView` loses `facts` (the drawer's JSON block replaces it); it keeps `summary`, `changes`, `unchanged`, `link`.
**`Drawer`** (Task 3 produces, Task 4 consumes), `frontend/src/components/Drawer.tsx`:
```tsx
export function Drawer(props: { title: string; onClose: () => void; footer?: ReactNode; children: ReactNode }): JSX.Element
```

## Rulings taken while planning (each is also a `Ruling:` line in the ledger)
- **R1 `refs` rides on each item, not one object per page.** Why: a list item, the neighbour the drawer steps to and the entry fetched by id are then the same self-contained shape; the lookup is still one batch per kind per page. Cost if wrong: a slightly larger JSON (a few short strings per row).
- **R2 A name stored in the entry's detail (`name`, `username`) beats the ref.** Why: it is the name at the time of the event ("Deleted asset Panel A" must keep saying Panel A). Refs only fill sentences that carry nothing but an id. Cost: a renamed asset shows its old name in old entries (correct for a log).
- **R3 Writers are NOT changed to store names at write time.** Why: the owner asked that a gone target read "a deleted asset"; `asset.deleted`, `source.deleted` and the others already keep the name in their own entry; changing stored details touches six writers and their exact-detail tests for little gain. Cost: a tariff entry for a since-deleted asset says "for a deleted asset" instead of naming it. Parked in the backlog.
- **R4 Kinds are asset, user, source, dashboard, point; roles and scan scopes are not looked up.** Why: every writer already stores `name` for roles and scopes; the matcher falls back to the plain noun ("role", "scan scope"), never to "#4". Mappings and tariffs have no name: they are described by their point and asset ("the mapping of point Voltage L1", "the tariff for asset Panel A", "the site default tariff").
- **R5 No "unknown" id ever shows.** With a lookup (`refs` defined): found = the name, absent = "a deleted asset". Without one (`refs` undefined, only in tests or a future caller): the plain noun with an article ("an asset"). Fields in the Before/After table that hold an id (`parent_id`, `asset_id`, `user_id`, `source_id`, `dashboard_id`, `point_id`) are shown as a label without "id" ("Parent asset", "Asset") and a name or "a deleted asset" or "—"; a `dashboard_id` row is dropped when the same entry also has the `dashboard` name field (it would say it twice).
- **R6 A link to a target that is gone is not shown** ("Open asset X" for a deleted asset led to a not-found page). Cost: old create entries of deleted assets lose their link.
- **R7 `Scan #N` stays** (see Global Constraints). The entry's own number stays in the drawer with a Copy button (the owner asked).
- **R8 The route is ONE route, `/audit/:id?`.** Why (corrected by the plan review): one declaration, it does not depend on React Router's unkeyed reconciliation of two sibling routes (the review's harness on 7.18.4 showed two siblings would also keep one instance), and it is the pattern `/users/:tab?` already uses (`App.tsx:69`). `pageTitle` already treats `/audit/12` as the Audit log, and `Layout` has no focus or scroll effect on a path change (checked).
- **R9 History:** opening pushes `/audit/ID?<same query>` with `state {fromList: true, search}`; Previous and Next REPLACE (Back must not walk every entry); Back closes. Closing: `navigate(-1)` when `state.fromList` and the query string is still the one it was opened with, else `replace` to `/audit?<current query>` (a deep link, or a Next that crossed a page).
- **R10 (corrected by the plan review, I1) While the drawer is open, `.shell` and `.skip-link` get `inert` (removed on close, StrictMode-safe, counted for nested opens); NEVER `#root`.** Why: the brief says the page behind is dimmed and inert; the toast stack is a sibling AFTER `{children}` of `ToastProvider` (`Toasts.tsx:188-195`), outside `.shell` (`Layout.tsx:130`) and the skip link (`Layout.tsx:120-129`), so the drawer's own toasts stay live and closable. The focus trap and `aria-modal` stay as a backstop and focus inside `.toast-stack` is allowed. The drawer sits at z-index 800 (the toasts' own CSS reserves "at most 800" for it: stack 900, dialogs 1000).
- **R11 The entry is fetched by id only when it is not in the loaded page.** Why: list items are complete (R1), so a second request adds nothing; a deep link to an entry on another page fetches it. Previous and Next are DISABLED in that case with the reason in the accessible name (the list behind shows the first page; we do not know the entry's position). Cost: a deep-linked entry cannot be stepped from; parked.
- **R12 Previous = the entry above (newer), Next = the entry below (older)** (the list is newest first, like the pager). At the edge of a page the neighbouring page is fetched (`queryClient.fetchQuery`, same key as `useAudit`) and the drawer moves into it; at the very ends the button is disabled ("Previous entry: this is the newest entry"). A fetch error shows a short line in the drawer's footer and changes nothing.
- **R13 The drawer keeps the Before/After table for updates** (the brief lists JSON only, but the table is the friendly account of an edit) and drops the old "facts" list (the JSON block shows the same data).
