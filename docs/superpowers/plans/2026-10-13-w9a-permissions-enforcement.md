# W9a: roles and permissions, part 1 (enforcement) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every API route is gated by a named permission instead of a three-step role; Viewer, Operator and Admin stay exactly as they are (locked, built-in) and the server, the database and the front end are ready for custom roles (the Roles page itself is W9b).

**Architecture:** A permission catalogue on the server (`backend/dcdash/core/permissions.py`, 28 ids) is the single source of truth. Migration `0009` adds a `roles` table and `users.role_id` (NOT NULL), seeds Viewer, Operator and Admin and drops `users.role`. The user query loads the role with the user (a joined eager load), `require_permission` / `require_any_permission` replace `require_role` on all routes, a frozen matrix fixture (generated from the CURRENT code before anything changes) proves the three built-in roles get the identical answer on every route, and a coverage gate fails the build for a route with no declared permission. A roles API with its safeguards (last Admin, in-use delete, subset rule, audit) lands in the same wave; the front end swaps `hasRole` for `can(permission)`.

**Tech Stack:** FastAPI 0.142 + SQLAlchemy 2 async + Alembic + asyncpg/testcontainers (pytest), React 18 + Vite + vitest, Playwright e2e.

**Spec:** `.superpowers/sdd/overnight-w7/W9-roles-permissions.md` (the owner's decisions D1 to D3, the design, W9a's five tasks, the review focus). Read it. This plan refines it; where they differ this plan wins (see "Rulings taken while planning").

## Global Constraints

- **The owner's decisions are fixed (do not reopen):** D1 "level 2 plus a few risky splits" (a SEE and a CHANGE permission per area, a handful of separate risky actions; 28 permissions in all); D2 Viewer, Operator and Admin are built in, locked (not editable, not deletable), duplicable; Admin is "all permissions" computed from the catalogue at run time; D3 only Admin manages roles in this version (`roles.manage` exists but a custom role can never hold it), one role per user, no per-site or per-asset scoping (say so in the docs).
- **ZERO behaviour change for the three built-in roles**, in the API (the frozen matrix) and in the UI (the same sidebar items, routes and buttons for each). Role names stay `viewer`, `operator`, `admin` (lower case) and `/api/me`, login and setup keep answering `role: "<name>"` and add `permissions: string[]`.
- **No route without a gate.** A route is either in the explicit PUBLIC list (no sign-in), in the explicit SIGNED_IN list (any signed-in account), or declares `require_permission(...)` / `require_any_permission(...)`. The build (a test) fails otherwise.
- **Unknown or forbidden permission strings stored in a role are IGNORED at run time, never granted** (unknown ids; `roles.manage` on a custom role). A built-in role's permissions come from CODE (`permissions.BUILTIN`), never from the stored `permissions` column; the stored column of a built-in row is an informational mirror.
- **Server first.** The UI is never the only gate; the front end hides or disables what the server would refuse and never hides what the person may do.
- **Migrations:** the next free number is `0009`; head is `0008`. The migration file imports nothing from `dcdash` (it is frozen history; permission ids are literals in it). Rehearse upgrade, behaviour, LOSSLESS-as-far-as-possible downgrade and upgrade again on a restored copy of the dev DB (controller step).
- **Audit:** every role create / change / delete and every change of a user's role is audited with the permission difference in the details (`audit` / `audit_change` in `dcdash.core.audit`), and readable in the friendly view (`frontend/src/lib/auditText.ts` + `auditKind.ts`, both have tests that list every action).

## Review Focus

Failure modes the owner's words imply that no task's happy-path tests exercise; each has a named test in the owning task.

1. **A route nobody gated** (a new or forgotten route, a router-level dependency lost in the switch, the stream that authenticates by hand). Task 2: the coverage gate + `ROUTE_PERMISSIONS` table equality in both directions.
2. **A built-in role changes** (a route Operator could call that it now cannot, or the reverse; a viewer reaching an admin route through a shared permission). Task 1 freezes the matrix BEFORE any change; Task 2 asserts equality.
3. **Escalation.** A `users.edit` holder resets the Admin's password / deactivates / deletes an Admin / gives itself or anyone Admin; editing a role to add what one lacks; duplicating Admin (copy must lose `roles.manage`); renaming a built-in; changing one's own role. Task 3.
4. **Stale authority.** A permission removed while a request or the live stream is in flight; a deactivated user; a role deleted while assigned; an unknown permission string in the database; a user whose role row cannot be read. Task 2 (stream re-check, per-request read), Task 3.
5. **The last Admin** deactivated, demoted or deleted from two sessions at once (the advisory-lock pattern of `users.py`), and deleting a role in use (409) racing an assignment. Task 3.
6. **Information leaks.** `/api/me` carries only the caller's own permissions; the role list shows other roles' permission lists only to `roles.manage`; 403 bodies are the same short text for every missing permission; `GET /api/permissions` needs `roles.manage`. Task 3.
7. **No flash of forbidden content** (the sidebar, the landing page, a page open when the permission set changes) and a role with NO permissions gets a plain "Your role has no pages yet" screen, not a blank page or a redirect loop. Task 4.

## Rulings taken while planning

- Ruling: 28 permissions, ids `area.action` (Appendix A). The owner's draft table is the base; the additions are the ones the route inventory forces so that Operator behaves as today: `tariffs.view` (Operator reads `GET /api/tariffs`), `sources.test` (test, test-all), `diagnostics.run` (the connection check, an Operator route), `dashboards.default` (the admin-only default dashboard), `discovery.edit` (scopes, layout; admin-only). — cost if wrong: one id fewer or more in the catalogue; ids are strings in one file.
- Ruling: built-in role names are stored lower case (`viewer`, `operator`, `admin`), names are unique ignoring case (`lower(name)` index), built-in ids are 1, 2, 3. `/api/me.role` is the NAME, so no client and no existing test changes. — cost if wrong: a display label helper later.
- Ruling: built-in permissions come from code (`permissions.BUILTIN`), Admin = `ALL_IDS`. The seed rows store a mirror (informational) and a parity test pins viewer and operator mirrors to the code. — cost if wrong: a new permission for Operator needs a code change and a migration, which is what D2 asks for.
- Ruling: users accept a role by NAME (`role: "viewer"`, matched ignoring case) in `POST /api/users` and `PATCH /api/users/{id}`; no `role_id` yet. Every existing test and e2e call keeps working. — cost if wrong: add `role_id` later (W9b can).
- Ruling: `User.role` stays readable as a property (the role's name) and `User.permissions` is a frozenset; the mapped column is `role_id` and the relationship `role_row` (`lazy="joined"`, `innerjoin=True`), so the user query that authenticates also loads the role (no second round trip).
- Ruling: the live stream becomes a dependency with its OWN short-lived session (a dependency that holds the request's session would keep a connection open for as long as the browser stays connected, the reason the route authenticates by hand today); its periodic re-check also re-reads the permission, so a removed permission ends an open stream within a minute. Permission: any of `assets.view`, `dashboards.view`.
- Ruling: `GET /api/jobs/{id}` needs any of `sources.test`, `diagnostics.run`, `discovery.scan`, `sources.edit` (every kind of job the API starts needs one of them; Operator holds two, Viewer none, as today).
- Ruling: `GET /api/status`, `GET /api/site`, `GET /api/version` become SIGNED_IN (any account), because every role could call them as Viewer. A role with no permissions can therefore read the site name, the version and the collector-alive chip.
- Ruling: the front end keeps each built-in role's pages exactly: page access uses the permission of the page's heaviest call (Sources page `sources.view`; a source's points page `sources.edit`; Scans and Discovery `discovery.view`; Tariffs `tariffs.edit` (the page also reads the currency, an admin-only route; a read-only Tariffs page for `tariffs.view` alone is parked for W9b); Storage `storage.view`; Settings `settings.view`; Users `users.view`; Audit `audit.view`; Diagnostics `diagnostics.view`).
- Ruling: a user may only change (password, active, role, delete) an account whose role holds no permission the actor lacks, and may only assign a role whose permissions the actor holds ("the subset rule"); changing one's OWN role is refused (409). Without the first half, `users.edit` would be a way to take over Admin by resetting its password. `POST /api/users/{id}/unblock` follows the manage-target rule too (see Amendment C1): lifting the lock-out of a stronger account would let the caller keep guessing its password.
- Ruling: `GET /api/roles` is open to `roles.manage`, `users.view` and `users.edit` (the Users page's role select), and carries `permissions` only for `roles.manage`; every row says `assignable` (the caller holds all of that role's permissions).
