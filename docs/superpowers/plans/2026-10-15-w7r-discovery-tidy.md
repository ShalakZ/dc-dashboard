## Facts checked in the code (LESSONS A12: the brief is not law)

- **Scans.** `api/scans.py::scan_summary` returns `scope_name` only (from the snapshot). `start_scan` stores `{scope_name, targets, ports, hosts, pairs, digest}` in `scans.scope_snapshot`; `GET /api/scans/{id}` already returns the raw `scope_snapshot`, `GET /api/scans` does not, so one additive pair of keys in `scan_summary` serves both. `ScanProgress.tsx` is used only by `ScansPage.tsx:155`; `activeScan` is set by "Details" and by a started scan (`:60`) and never cleared. The stats line prints `progress.checked/pairs` as "ports checked": it counts probes (hosts x ports). Recent scans prints `claimedCount(progress) / progress.points` under "Claimed / points" (`ScansPage.tsx:165,172`).
- **Graph.** `GET /api/discovery/graph` (`api/discovery.py:120`) lists every source (`select(Source)`), with `latest_outcome` from the newest finding per source (`func.max(ScanFinding.id)` grouped by `source_id`). `GET /api/sources` hides a discovered source with no mapped point (`_has_mapped_point`, `api/sources.py:119`). `ScanFinding.source_id` is `ON DELETE SET NULL`, `Scan` has `created_at` and `finished_at`. `graph_layout.node_id` is a plain string key with no foreign key: ids look like `src:12`, `cluster:12:<name>`, `point:345`, so removing a source leaves orphan layout rows unless the route removes them (`delete_source` does not either).
- **Delete rules to copy.** `_lock_source(db, id)` locks the source row, then its points `ORDER BY id FOR UPDATE`; a mapping being added holds `FOR KEY SHARE` on its point, so the two meet; `_mapped_counts` is its own statement and sees what committed while waiting. `delete_source` audits `source.deleted` `{source_id, name, points, mappings}` and calls `notify(db, CONFIG_CHANNEL)`. The friendly text `source.deleted` -> "Deleted source <name>" (`auditText.ts:631`, `removed("source", "source_id")`, the name comes from `detail.name` when the source is gone) already exists; reusing the action changes no frozen audit test (`auditKind.test`, `auditText.test`, `test_audit_coverage`).
- **`_adopt`** (`collector/scan.py:216`) builds `index[key] = (id, origin)` with `setdefault` over `ORDER BY id`: the oldest source wins whatever its origin. A discovered finding goes into `to_browse`; a manual match gets `detail "existing source"` and is never touched. Only the origins `manual` and `discovered` exist (`Source.origin`, default `manual`).
- **R7, "Enabled" ticked.** `SourceForm.tsx:26` defaults `enabled` to `source?.enabled ?? true` only for a NEW source; an edit starts from the source's own value. `_insert_source` creates discovered sources disabled, but `POST /api/discovery/accept` sets `source.enabled = True` (`api/discovery.py:222`) and the Sources list shows a discovered source only after a point is mapped: every discovered source the edit dialog can open was enabled by mapping. Not a bug; no fix (Ruling 12g); the docs say so in one sentence.
- **Node buttons.** `MapButtons` (`graph/nodes.tsx:32`) render "Map..." and "New asset..." as ordinary buttons (no hover needed) but only on a CLUSTER node of an EXPANDED source and on a point node of an expanded cluster, admins only (`discovery.accept`). A collapsed source node offers only "Details". Nothing on the page says "click"; `HINT` says only "Drag nodes to arrange them" (`DiscoveryPage.tsx:24`). `dropPayload(model, id)` already turns a cluster or point id into `{source, points (unmapped only), label, kind}`; `acceptBody` and `reviewRows` build the accept call from it.
- **Page CSS.** Scans and Discovery chrome live in `styles/pages-sources.css` under bare class names (`.scan-detail`, `.gpanel`, `.graph-page`); the app.css clash test allows one page class per page file, so each task below owns a NEW file (`scans-drawer.css`, `discovery-tidy.css`, `bulk-assets.css`) created in the scaffold and imported in `main.tsx` next to `drawer.css`.

## Decisions taken here (the brief stands; these refine it; the owner may overrule any)

1. **Order.** Plan -> ONE Opus plan review -> fold in -> S0 scaffold -> Wave A (T1 backend, T2 Scans, T3 Discovery, T4 bulk-create dialog, all in parallel; disjoint files) -> T5 e2e (parallel with T6 docs) -> gates -> whole-wave review -> fix wave -> merge. The detached full backend suite starts as soon as T1 is committed and no backend edit is in flight (nothing else touches `backend/`); it is rerun only if the fix wave changes `backend/`.
2. **Scan Drawer (R1).** New `components/ScanDrawer.tsx` replaces `ScanProgress.tsx` (deleted in T2): `Drawer` with the title `Scan #7 - done` (kept so the heading needle `Scan #7 — done` of `ScansPage.test.tsx:250` still holds; the title follows the status live), the body = what `ScanProgress` showed (scope line, stats line, stage while running, findings table, the link "Open the discovery graph"), live for a running scan (`useScan` keeps polling every second). While `useScan` has no data the drawer shows a skeleton of the same shape (title `Scan #7`); a failed read is a `role="alert"` line. `ScansPage` renders `{activeScan !== null && <ScanDrawer ... onClose={() => setActiveScan(null)} returnFocus={...} />}`; `returnFocus` returns the Details button of that scan's row (`data-scan-details="<id>"`), null when the row is not there (then the Drawer falls back to `#main`). A scan that was just started opens its drawer as today (the old box appeared on start too); closing it never stops the scan. No deep link (Ruling 12a). The Details button keeps its name "Details".
3. **Numbers and the scope (R2).** Server: `scan_summary` gains `targets: list[str]` and `ports: list[int]` from the snapshot (`[]` when the snapshot has none). Front end (`lib/scanText.ts`, pure, table-tested): `scopeLine(name, targets, ports)` = `Simulator: 172.20.0.0/24, ports 9000, 4840, 5020` (singular `port 9000`; at most 4 targets and 8 ports, then ` and N more`; no targets and no ports -> just the name); `sourcesAndPoints(progress)` = `1 source, 60 points` (plural-aware, `0 sources, 0 points`); `checksText(progress, running)` = `762 checks (254 hosts x 3 ports)` when done and `pairs == hosts * k` for an integer k, `310 of 762 checks` while running, `762 checks` when the split is not exact or hosts is 0. The drawer's stats line: `checksText`, `N open`, `N sources read` (= `claimedCount`), `N points`, `N need credentials`, `N unidentified`. Recent scans: the column header `Sources / points`, the cell `sourcesAndPoints`, a `title` with the longer wording ("1 source recognised and read, 60 points found"); no `aria-label` (a generic element's label is ignored by assistive technology; the text is already a full phrase; Ruling 12b). The Scope cell shows the name and, under it, a muted `targets | ports` line (`.cell-sub`, ellipsis, the full text in `title`).
4. **Remove and Clear unmapped (R3), one route.** `POST /api/discovery/sources/remove`, permission `discovery.edit` (no new permission, no migration), body `{"source_ids": [int, ...]}` (1 to 500 entries, duplicates folded, Pydantic 422 otherwise). The server sorts the ids ascending and, for each, in ONE transaction: `_lock_source` (a gone source -> skipped `gone`), then `origin != "discovered"` -> skipped `manual`, then `_mapped_counts` (its own statement) with `mappings > 0` -> skipped `mapped`, else `db.delete(source)` (points go with it), the `graph_layout` rows `src:<id>`, `cluster:<id>:%` and `point:<each point id>` are removed, and ONE audit row `source.deleted` `{source_id, name, points: 0, mappings: 0, unmapped_only: true}` is written per removal. One `notify(db, CONFIG_CHANNEL)` and one commit at the end when anything was removed. Answer 200 `{"removed": [{"id", "name"}], "skipped": [{"id", "name" (null when gone), "reason": "mapped"|"manual"|"gone"}]}`. The client sends the ids it LISTED in its dialog, so a source created by a scan after the dialog opened is never touched, and a source that gained a mapping since is kept: that is the stale guard (nothing with a mapping can be removed by this route, whatever the client sends). Findings keep their rows (`source_id` becomes NULL); past scans still read the same. The existing `DELETE /api/sources/{id}` and its dialog are unchanged.
5. **Front end of Remove and Clear.** A source is *removable* when `origin === "discovered"` and no point of it has a `mapping_id` (pure `isRemovable(source)` in `lib/graph.ts`). For `can("discovery.edit")`: a quiet `Remove` button on a removable source node (next to Details, `aria-label="Remove <name> from Discovery"`), and `Clear unmapped (N)` in the page header actions beside Refresh (`aria-disabled` plus a click guard and a title "Nothing to clear" when N is 0: never native `disabled`, never a slot that appears and disappears). Both open `ConfirmDeleteDialog` (confirm label `Remove`): one source -> title `Remove "<name>" from Discovery?`, message `It has nothing mapped, so no asset, billing figure or dashboard depends on it. A scan can find it again.`; several -> `Remove N unmapped sources?` with the first 5 names, ` and N more`, then `Sources with a mapped point are never touched. A scan can find these again.` The list is FROZEN when the dialog opens (state), and that list is what is sent. Result: all removed -> dialog closes, toast `Removed 3 sources`; some skipped -> dialog closes, error toast `Removed 2 sources. 1 was kept: it has a mapped point now.` (reasons in words, `manual` -> `it was added by hand`); nothing removed -> the dialog stays open and shows that sentence as its error. After any answer `keys.graph`, `keys.sources` and `keys.auditAll` are invalidated once. Focus after the dialog: the Refresh button (the node that held it is gone); a closed Source panel for a removed source follows from `selected` being undefined.
6. **Last seen (R4).** `GET /api/discovery/graph` sources gain `last_seen: {scan_id, at} | null` = the newest finding of that source (`max(ScanFinding.id)` as for `latest_outcome`), `at` = the scan's `finished_at` or else `created_at`. The node's muted line reads `Seen in scan #6, 10 minutes ago` (`relativeTime` with the site time zone; over 14 days or unreadable it drops the ago part), `Added by hand` for `origin === "manual"` (whatever its findings), `Not seen in a scan yet` for a discovered source with `last_seen == null`. The source panel shows the same line.
7. **Manual wins (R5).** In `_adopt`, `index[key]` is set when the key is new, or when the stored entry is discovered and the row is manual; a later discovered row never replaces anything and two manual rows keep the oldest. Nothing else changes: the finding for a manual match stays `existing source`, the older discovered duplicate is not in `to_browse` any more (it keeps its points and stays on Discovery until cleared), no row is merged, moved or deleted by the scan. Test order: discovered first, manual later.
8. **Click to create (R6).** (a) `HINT` becomes `Dashed nodes were discovered; solid nodes are assets. Open a source with +, then press New asset... on a group to turn it into an asset, or drag it onto an asset to map it. Drag other nodes to arrange them.` (b) A source node with at least one *mappable cluster* (not Ungrouped, at least one unmapped point, `can("discovery.accept")`) gets a `Create assets...` button (`aria-label="Create assets for N groups of <name>"`), reachable on the COLLAPSED node, so the path is click, not drag. It opens `BulkCreateDialog` (T4): ONE chosen parent (or root), a row per mappable group (a checkbox, an asset name defaulting to the group's name, the number of points, the metrics the scan guessed), `Create N assets`. One `POST /api/discovery/accept` per group, in order (a client loop over the existing route; each call is atomic; `reviewRows` supplies the metrics and scales; points it leaves unchecked because a metric repeats stay unmapped and the row says so); partial failure is reported per row (the server's message, e.g. a name already used under that parent) and the created rows leave the list; the three keys are invalidated once. No new backend route (Ruling 12c); the brief's two-hour fuse is not tripped; if T4 is not done and green by 13:00 the button is parked (backlog) and nothing else changes (Ruling 12d).
9. **Permissions.** Reading stays `discovery.view`. Remove and Clear: `discovery.edit`. Create assets: `discovery.accept` (as the Map buttons). The route sits in `auth_expectations.py` `_all("discovery.edit", ...)`; the permission matrix and coverage gate take it from there. `PERMISSION_NEEDS` and the permission count are untouched (no new permission).
10. **Process notes.** No Playwright from implementers; T5 writes `frontend/e2e/w7r.spec.ts` with its own project `w7r` as the LAST project of `playwright.config.ts` (its Clear unmapped removes every unmapped discovered source of the shared e2e stack).
11. **Docs** (T6): `docs/sources-and-discovery.md`, `docs/screens.md`, `docs/roles-and-permissions.md` (the `discovery.edit` row), `CHANGELOG.md` (section `W7r`, newest first, the merge commit filled in after the merge), backlog section AQ, roadmap row O-36, this plan's log. README untouched unless a doc test says otherwise.
12. **Rulings.** (a) No deep link to a scan (the audit entry has one because the log is a list of events; a scan is opened from its row; cost if wrong: no pasted link). (b) No `aria-label` on a table cell (ignored by assistive technology); the visible text is the full phrase. (c) Bulk create is a client loop over `accept` (a batch route would add a permission row, a transaction test and a half-done state for no visible gain). (d) The bulk button is parked if not green by 13:00. (e) `source.deleted` is reused for the removal (the friendly text, the icon and the audit filters already know it; `unmapped_only: true` tells it apart in the stored JSON; cost if wrong: the log cannot filter "removed by cleanup" alone). (f) Hand-added sources say "Added by hand", not a last-seen time (a scan that finds one only reports `existing source`). (g) R7 is by design (see the facts). (h) The unidentified-service nodes are not sources and are not cleared; they leave Discovery with the next finished scan.

## Plan review fold-in (Opus, `plan-review-report.md`: 2 Critical, 7 Important, 10 Minor; every item folded in; the F items OVERRIDE the earlier text wherever they differ)

- **F1 (C1) A scan interlock on the remove route.** `run_scan` writes all findings at the end in one INSERT whose `source_id` is a real foreign key, and the browse stage takes the source's point locks in the opposite order to `_lock_source`: a removal during a scan would fail the scan and lose its findings (or deadlock). The route therefore starts with `SELECT pg_advisory_xact_lock(:key)` on `SCAN_START_LOCK` (imported from `dcdash.api.scans`; `start_scan` takes the same lock) and answers `409 "A scan is running. Remove discovered sources when it has finished."` when any scan is `queued` or `running`, before any row lock, removing nothing. Test: a running scan row -> 409, nothing removed, no audit row. Front end: the 409 text is the delete dialog's error line (the "nothing removed" case, the dialog stays open). Docs: one sentence.
- **F2 (C2) `accept` locks the source first.** In `api/discovery.py::accept` the `get_source` call becomes `select(Source).where(Source.id == body.source_id).with_for_update(key_share=True)` (renders FOR NO KEY UPDATE; it does not block the collector's point inserts, which take KEY SHARE); `None` -> `404 "source not found"`. Every path now takes the source before its points, so `accept` against `remove` ends in exactly one of two ways: `accept` first (remove waits, then `skipped: mapped`) or `remove` first (`accept` gets 404).
