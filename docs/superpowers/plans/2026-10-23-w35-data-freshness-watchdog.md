## Rulings of this plan (on top of R1 to R12)
- **A. Never-read meters.** A billing meter without a `point_latest` row is "waiting": counted in `meters`, never stale, never not-advancing. A row with `good_at` NULL (only BAD readings, and none Good in the back-fill's 7 days) IS stale at once. Cost if wrong: a point whose collector never writes even a BAD row stays silent here (the `source.offline` / `points.bad` incidents cover it).
- **B. Freshness of the "no load" twin.** The twin power mapping of the same asset counts when its `good_at` is within `max(3 x its interval, floor)` and `abs(good_value * scale) <= 0.05`. Twin on a disabled/file source: not fresh, no suppression.
- **C. Frozen source.** A source's considered counters = its billing counters that are not "no load". Frozen = considered >= 2 and every one not-advancing (so none of them is stale). Stale-level counts: `meters_stale = stale meters + considered counters of frozen sources`; `meters_not_advancing` = not-advancing counters outside frozen sources. `oldest_stale_age_seconds` = max over stale meters of their Good age (NULL `good_at`: skipped) and over frozen counters of their `changed` age; NULL when none has an age.
- **D. Verdict cache.** One process-level cache of the verdict, 5 s, an `asyncio.Lock` so a burst waits for one query; `reset_cache()` for tests (an autouse fixture in `tests/conftest.py` calls it); the PUT of the setting clears it. The verdict includes the settings row and `rollups_late`. If the verdict query raises, `/api/status` answers with the new fields null (the chip then behaves as today); the URL answers 503 `unavailable`.
- **E. Event ownership.** `data.stale`, `data.recovered` (both T4) and `readings.dropped` (T6): ALL THREE constants and their words in `eventText.ts` + parity test are added in T4, so T6 only emits.
- **F. Incident writes.** The worker step runs at most every 60 s; each run recomputes the verdict FRESH (not the 5 s cache), then per source: trouble -> open or bump (level `error` if any stale-level meter else `warning`); a source judged and clean -> close with `closed_by = recovered` plus ONE `data.recovered` event; an open row whose source is not judged any more (disabled, deleted, file, no billing meter) -> close with `closed_by = polling_stopped`, no recovery event. All three in the same statement shapes as `_OPEN_OR_BUMP` / `_CLOSE_OPEN` (own SQL, kind `data.stale` NOT in the book's `KINDS`).
