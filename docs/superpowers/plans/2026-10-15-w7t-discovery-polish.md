2. **Crumb icons (T1).** `Crumb` gets an optional `icon?: IconName`; `Crumbs` draws `<span class="crumb-icon" aria-hidden="true"><Icon name=.../></span>` INSIDE the link or the current-page span, before the label, so a link's accessible name stays its text (an `aria-hidden` svg adds none) and `a.textContent` is unchanged. Size `1em` of the crumb font, `flex: none`, colour `currentColor`; the link/span becomes `display: inline-flex; align-items: center; gap: 5px; min-width: 0` and the label stays wrappable (`overflow-wrap: anywhere`), the row height must not change (measured). On the asset page: the first crumb uses `assets`, every ancestor and the current asset use `assetIcon(row)` (ancestors from the cached list; the current asset from the summary's own `data.asset`, as the page title does). `AssetKindsPage`'s first crumb ("Assets Tree") gets `assets` too, so the two trails that start with it agree; every other trail keeps text crumbs (Ruling 9b: the Dashboards, Sources and Audit trails have no per-row icon to show and a lone section icon would make the sidebar's job twice; cost if wrong: add `icon` to one more array). No skeleton change (the skeleton's trail is text-height lines; the icon adds width only).
3. **Layout rules (T5 pure code, T6 page).** Positions are decided in `buildGraph(model, open, { moved, ignoreSaved })`, which replaces the page's after-the-fact `moved.current.get(id) ?? position` override. A node's OWN place is `moved.get(id)`, else (unless `ignoreSaved`) `model.layout[id]`. A node without an own place stands at `its default + (its parent's actual - its parent's default)` where the parent is source -> cluster -> point, parent asset -> sub-asset (the "parent" is the node THIS build descended from, not a `parent_id` lookup: source -> cluster -> point, and in the asset `walk` the stack entry carries its parent's id so the parent is already placed; a walk root, a self-parent, an orphan or a member of a cycle has none, review finding 4). `descendantNodeIds(model, id)` lists EVERY node under `id` in the model, open or not (`src:` -> its clusters `cluster:<sid>:<key>` INCLUDING `cluster:<sid>:__ungrouped__` when the source has ungrouped points, and the points `point:<id>`; `cluster:` -> its points; `asset:` -> all sub-assets by `parent_id`, cycle-safe; points and unidentified nodes -> none). **Drag (no Alt):** at drag start the page takes ONE SNAPSHOT: the start place of the dragged nodes, the set of followers = (the union, as a Set, of `descendantNodeIds` of every dragged node) intersected with the ids of React Flow's LIVE node list (`getNodes()` from `useReactFlow()`, not the render closure: the callbacks have `[]` deps) minus the dragged ids, their start places, and a copy of every own place (`moved` and `model.layout`, unless `ignoreSaved`) as it is at that moment; on every `onNodeDrag` the followers (never a dragged id) are set with `setNodes(cur => cur.map(...))` to `start + (primary's current - primary's start)` (React Flow's own position change for the dragged nodes and this update are both functional updates on the same state and compose; auto-pan keeps the followers up); at drag stop every shifted place that came from the snapshot (a visible follower with an own place, and every HIDDEN descendant with an own place) becomes `snapshot own + delta` and is written into `moved` FOR EVERY ROLE (the graph is not read again after a save, so without this a second drag would lose the first delta and re-opening a group would put it back at its old place: review finding 1), and with `discovery.edit` the same entries plus the dragged nodes go into the SAME request(s). The shift is computed from the snapshot, never from `moved` while it is being updated (a multi-selected source and its own cluster must not shift twice: review finding 2). Followers without an own place are NOT stored (they follow by the rule and are where the drag left them). One request carries at most 2000 nodes (a longer list is sent as several consecutive requests; ids over 512 characters are skipped as today). **All layout writes (the PUT batches and Tidy's DELETE) go through ONE promise chain** (`layoutWrites.current = layoutWrites.current.catch(() => {}).then(write)`), so a quick second drag or a Tidy cannot reach the server out of order, and Tidy waits for the chain before it sends. **Alt (Option) held at drag start** = alone: no followers, nothing else shifts; Alt is read once at the start and holds for the whole drag. **Drop on an asset (maps):** the dragged node AND its followers go back to their start places, no layout is saved. Dragging a child never moves its parent. Cost if wrong: a child that was dragged away keeps its own absolute place and a later parent drag moves it by the delta, as the owner's "each keeping its offset" says. **Known limit, parked on purpose (review finding 3, backlog AS):** a child with an own place under a parent WITHOUT one still stays put when a source ABOVE the parent opens and pushes the parent's default slot down (this is today's behaviour, not part of the owner's remark). Pinning every ancestor on each drag would trade a detached child for a pinned parent that a growing block above can cover; Tidy layout puts both right. A T5 case documents the behaviour so a later change is deliberate.
4. **Tidy layout (T4 backend, T6 page).** New `DELETE /api/discovery/layout` (204, permission `discovery.edit`, removes every `graph_layout` row, idempotent, not audited like the PUT it mirrors). The existing PUT cannot restore the default for a node that is hidden (collapsed groups with an old absolute place would re-open far from their parent), so a front-end-only Tidy would leave the very bug the owner reported. The page: a **Tidy layout** button in the new bar. With `discovery.edit` it first asks "Tidy the layout for everyone?" (`useConfirm`, confirm label `Tidy for everyone`: a label equal to the bar button's name would make `getByRole("button", { name: "Tidy layout" })` match twice while the dialog is open), waits for the layout write chain (Decision 3), then calls the route; on success it FIRST clears `moved` and sets `tidied` (so `buildGraph` already ignores `model.layout` and the old layout never flashes), THEN awaits the re-read of the graph and refits the view with the W7r opening rules (`initialView({ ...model, layout: {} })`) after the re-seed effect has run (the promise `fitView` returns, or a `requestAnimationFrame` after `setNodes`); if the re-read fails `tidied` stays set (the rows are gone either way). Without `discovery.edit` there is no question and no request: `moved` is cleared and `tidied` set (their own view only; a toast says so). A failed call leaves everything as it was and shows the server's reason (`role="alert"`). Cost if wrong: one more route; the owner asked for "the existing layout route", this does the same job completely.
