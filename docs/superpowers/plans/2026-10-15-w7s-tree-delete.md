## Facts checked in the code (LESSONS A12: the brief is not law)

- **What the owner saw.** LVP01 was the OPEN asset (`.node.is-selected`: `app.css:374` gives it `background: var(--accent-tint)` and a 3px left bar), LVP02/LVP03 were the picks (`tree-move.css:19`: the SAME `--accent-tint` plus a 1px frame). The count "2 picked" was right; the look told him 3. The Delete he pressed was the asset page's own (`assetActions` in `AssetsPage.tsx:52`), hence `Delete "LVP01"`. Picking exists only for Move (`PickSlot` in `AssetTree.tsx:285` offers `Move to...` and `Clear`).
- **Picking is gated by `assets.edit`**, nothing else: `move` (the whole feature bundle) is `undefined` without it, `kit` is null, no row is pickable, no `PickSlot`. Built-in roles: Viewer and Operator hold neither `assets.edit` nor `assets.delete` (`permissions.py:86-87`), Admin holds all, a custom role can hold `assets.edit` without `assets.delete`. So "the pick bar shows Delete only with `assets.delete`" can only be seen by Admin and by custom roles; the e2e case "no Delete" needs a custom role with `assets.view` + `assets.edit` (see w7p's role set-up, `e2e/roles.ts`).
- **The delete route** (`backend/dcdash/api/assets.py:176-223`): `GET /api/assets/{id}/impact` (`assets.delete`) returns `{assets, mappings, tariffs}` of the SUBTREE (the asset itself counts in `assets`). `DELETE /api/assets/{id}?confirm=true&expect_assets=&expect_mappings=&expect_tariffs=` locks the subtree, answers 404 "asset not found" when it is gone, 409 `{detail, assets, mappings, tariffs}` when any real count is HIGHER than the expectation (lower is fine), and writes ONE `asset.deleted` audit row `{asset_id, name, assets, mappings, tariffs}` per call. **Deleting a parent deletes its children**, so an id picked inside a picked parent answers 404 if it is sent after the parent: only roots may be sent (below).
- **Client helpers that exist:** `loadAssetImpact(id)` (`api/queries.ts:212`); `assetDeletePath(id, seen)`, `assetImpact(error)` (the 409 counts) and `assetLoss(impact)` (the sentence "N assets, M mappings and K tariffs will be deleted; their past energy and cost figures disappear from Billing and dashboards.") in `lib/impact.ts`; `toRoots(ids, index)` and `indexTree(tree)` (`has`, `parentOf`, `rankOf`) in `lib/treeMove.ts` (roots in tree order, ids not in the tree ignored); `visibleOrder(nodes, collapsed, visible)` in `lib/treeSelect.ts`; `namesLine(names, shown = 8)` in `lib/kindsBulk.ts`; `ConfirmDeleteDialog` (`message`, `loading`, `loadError`, `confirmLabel`, `onConfirm` whose rejection stays in the dialog, focus in / Tab wrap / Escape / focus back to the opener if it is still connected); `ImpactDeleteDialog` (single asset: `useQuery` with `gcTime 0`, a `refused` state when the server answers 409 with new counts); `useInvalidate()` (`api/queries.ts:262`, returns a promise); `useToast()` (`success`, `info`, `error`); `upperFirst` (`lib/upperFirst.ts`); `ApiError {status, detail, body}`.
- **The picks follow the list:** `AssetTree.tsx:530` `store.prune(byId.keys())` drops deleted ids from the picks as soon as the asset list no longer has them; failed or untried picks stay picked with no extra code.
- **Where the single delete navigates:** `AssetsPage.removed` leaves the page FIRST (`navigate("/assets")`) and only then refreshes (a refetch of the mounted summary of a deleted asset flashes a 404).
- **W7q's focus rule:** after a delete `focus({ preventScroll: true })` (an unscrolled focus call jumped the page to the top); Layout's `#main` has `tabIndex -1` and is the last-resort target (`useTreeMove.focusMainIfLost`).
- **Tree column geometry:** the pick slot is one fixed 32px line (`tree-move.css:9`; "350 picked" + Move to... + Clear fit the NARROWEST column, 220px = 201px of room, with about 17px spare), so a fourth item does not fit one line at the narrow end. The column's current width is `width.now` in `useTreeWidth` (`AssetTree.tsx:226`).

## Decisions taken here (the brief stands; these refine it; the owner may overrule any)

1. **The bar's Delete exists only while something is picked** (`count > 0`) and the viewer holds `assets.delete`; with nothing picked the bar keeps its hint and Move to... for the open asset, and the open asset's own Delete stays where it is (the page header). One place per meaning. No keyboard shortcut (S1). It is a text button "Delete" (accessible name "Delete the 2 picked assets": it contains the visible word), `type="button"`, `aria-disabled` plus a click guard while the page is locked (LESSONS A5), with the existing destructive styling (existing tokens only).
2. **Only roots are deleted.** `planDelete(ids, index)` reduces the picks with `toRoots`; a pick below another pick goes with its root. The dialog lists every picked name (title counts picks: `Delete 3 assets?`), says for each pruned pick `LVP02 is inside Data_Hall_1, which is also picked, so it goes with it.` (first 3, then `and N more are inside other picked assets, so they go with them.`), and the totals come from the roots' impacts only, so nothing is counted or sent twice (S2).
3. **Impact per root, with a small pool.** The dialog opens at once ("Checking what this deletes…") and asks `GET /api/assets/{id}/impact` for each root, at most 6 in flight, in a `useQuery` with the ImpactDeleteDialog's options (`gcTime 0`, `staleTime 0`, `retry false`, no refetch on focus). **The query key is `["impact", "assets-bulk", ...rootIds]`, outside the `["assets"]` prefix (F6): `run`'s own `invalidate(keys.assets)` must never refetch the numbers inside a dialog that is still open; a test pins it.** `loadImpacts` resolves a root whose impact answers 404 as `null` (already deleted by someone else); any other failure rejects and is a `loadError` ("Could not check what this deletes: …"), Delete stays off. **If any root is `null` (F3) the dialog is `blocked` (only Close) with `Some of the picked assets were already deleted by someone else. The tree has been refreshed; pick again.` and the hook calls `invalidate(keys.assets, keys.fleet)` at once (the useTreeMove.failedDrag precedent), so the vanished picks prune and the next Delete works.** No new batch route (R4).
4. **Cap: 100 roots** (`MAX_ROOTS`). Over it no dialog opens; an error toast says `Up to 100 assets can be deleted at once (you picked 140 top-level ones). Pick fewer.` (it counts roots, because a picked branch counts once). Cost if wrong: an owner with 150 test roots deletes in two rounds.
5. **Plain or not.** `sum` is the sum of the roots' impacts. Unpicked descendants = `max(0, sum.assets - picked.length)`. Plain = no unpicked descendants, `sum.mappings === 0`, `sum.tariffs === 0`: message = names + pruned notes + `This can't be undone.`, button `Delete`. Otherwise the message is names + pruned notes + `assetLoss(sum)` (verbatim, so the billing warning is the existing words) + `This can't be undone.`, button `Delete anyway`. While loading the dialog shows the checking line and the button `Delete` (no width change when the answer lands: the ImpactDeleteDialog rule).
6. **The loop** (`deleteAssetsOneByOne`): roots in tree order, ONE `DELETE assetDeletePath(id, seen)` at a time with the counts that root's impact showed (or the newer counts after a refusal); a 404 is "already gone" (counted, not a failure, the loop goes on); **the first other failure stops the loop** (R5: deletion is one-way; after a surprise the person looks again): that root is `failed {id, name, reason, now?}`, every later root is `notTried`. `now` is the 409's new counts (`assetImpact(error)`). Reasons are full sentences (the `sentence()`/`upperFirst` treatment of `kindsBulk.ts`, F-m7): 409 `More was added under it since the numbers were shown.`, 401 `Your session has ended. Sign in again.`, otherwise `upperFirst(error.message)`. The sum of `seen.assets` over the deleted roots is `assets` (how many assets went, as the dialog counted them: the DELETE answers 204 with no body, so the toast says what was shown; the audit row has the exact number). **Do not reuse W7q's `notTried` semantics: here `notTried` excludes the failing root.** `deleteAssetsOneByOne(items, { onRemoved })` calls `onRemoved(rootId)` right after each root is deleted or answers 404 (Decision 8).
7. **What the dialog does with the result (F6).** "Went" means `deleted.length > 0` (a 404 does not count: nothing was deleted by this press). Not went and there is a failure: if it carries `now` (a root grew) the dialog shows the new numbers (a `newer` map overrides that root's impact) and throws `More was added while this was open. The numbers above are updated; delete again to confirm.` (the single dialog's sentence), nothing is deleted; any other failure throws `Error(<name> + reason)` and the dialog stays open and shows it (this also covers "A was already gone, then B refused": the dialog stays with B's new numbers, and a second confirm sends A again, gets its 404, and deletes B). Not went and no failure (every root answered 404): `onDone`, info toast `Those assets were already deleted.`. Went: `onDone(result)`, the dialog closes, one toast: no failure -> success `Deleted 3 assets` (`Deleted 41 assets` when branches went: the counts the dialog showed; ` 1 was already gone.` appended for 404s); a failure -> ERROR toast `Deleted 2 assets. "LVP03" could not be deleted: <reason> 1 was not tried.` (the not-tried clause only when there are some; the reason already ends in a full stop; with 404s as well: `Deleted 2 assets, 1 was already gone. "LVP03" could not be deleted: ...`). `bulkRemoveToast` is pure and a table test pins these, including "deleted 0, gone 1, failed" (never "Deleted 0 assets").
8. **Navigate as soon as the open asset's root is gone; invalidate once after the loop (F5).** `useTreeDelete.run` passes `onRemoved` to the loop: when the root just deleted (or answered 404) is the open asset or an ancestor of it, `navigate` to the parent of that root (`/assets/<parent>`; `/assets` for a top-level root) (R7) AT ONCE, not after the loop: the open asset's chart polls every 10 s and a long loop would show a "not found" behind the dialog. The open asset id is read through a ref at that moment (Back can have moved the page), navigation happens once, and never when that root's delete failed or was not tried. Then, after the loop, `await invalidate(keys.assets, keys.fleet, keys.billing, keys.widgetData, keys.tariffs, keys.auditAll, keys.graph, keys.sources)` in a `finally` (the set `useMoveAssets` refreshes plus `keys.sources`, because point rows carry their mapping (F-m8; the single delete has the same gap: backlog); also after a partial failure and when nothing went: the screen may be out of date). `run` and the dialog's `confirm` carry an in-flight ref (a double press sends nothing twice), and `navigate` and the refocus are guarded by a mounted ref (a 401 or Back can unmount the page while the loop runs). `leaveTo` is the pure rule `onRemoved` uses.
9. **Focus (S4, W7q's rule).** At the press the tree computes `focusAfter` (`focusAfterDelete`): the first surviving row after the first picked row in the visible order (a picked row's whole subtree counts as picked), else the last surviving row before it, else `null`. **ONE refocus chain for every way the dialog can end (F4)**, run in an effect after the render that removed the dialog (so the dialog's own clean-up cannot undo it; the `useTreeMove.refocus` pattern; `useTreeMove.cancelDialog` is the precedent): (1) the opener (the bar's Delete button) if it is still connected, for Cancel and a partial result; skipped after a FULL success (every pick is gone, so is the button); (2) `ul.tree a[href="/assets/<focusAfter>"]`; (3) `#asset-tree-filter`; (4) `#main`; always `focus({ preventScroll: true })`. `ConfirmDeleteDialog` restores focus to `document.activeElement` as read at ITS first render, not to our `opener`, with a plain `focus()`, so the chain does not rely on it. A refocus also arms a one-shot check: after the next asset list lands (an effect keyed on `assets`), if the focus is on `<body>` (the Delete button went away a tick later: the last pick pruned after a window-focus refetch, a 403 that turned `remove` off, every asset deleted so the filter unmounted) the chain runs again from step (2). Unit cases: Cancel after the last pick was pruned, a partial result followed by loss of the permission, deleting every asset. The page does not scroll (the slot sits in the sticky column).
10. **The open row looks different from a pick (S3).** `app.css` `.node.is-selected` loses `background: var(--accent-tint)`: the open row keeps the 3px accent bar, the bold `--accent-ink` name and the accent icon; a pick keeps tint + 1px frame; open + picked is bar + frame + tint (the existing `.node[data-picked].is-selected` rule). No new token. Ink on the tree column's ground (`--bg`, `app.css:333`) AND on `--surface` (the open row now takes `.node:hover { background: var(--surface) }`) must reach 4.5:1 in all eight looks (4 presets x light/dark): two new pairs in the `textPairs` loop of `themes.css.test.ts:62-102` (no new harness), and the stale comment "the marker on the accent tint (selected tree row)" at its line 127 is reworded. `aria-current` stays. The bar's count text keeps `N picked`; while `count > 0` and an open asset exists and is NOT picked, the count carries `title="The open asset is not counted unless it is also picked."` and a `sr-only` sentence `The open asset, <name>, is not counted.` in the group (sighted and screen-reader users get the same fact).
11. **The bar at the narrow end: a CSS container query, not a JS width (F1).** `useTreeWidth` starts at the default 280 and measures in an effect, so a JS threshold paints one line first and two lines a frame later, and the loading skeleton's slot (always one line) would not match. Instead: `container-type: inline-size` on `.tree-body` (a block child; the column has an explicit width, so containment changes nothing else), a class `has-delete` on `.tree-slot` when `remove !== undefined` (the same class on the skeleton's placeholder slot), and in `tree-move.css` `@container (max-width: 268px) { .tree-slot.has-delete { height: 64px; flex-wrap: wrap; align-content: center; row-gap: 2px } }` (the repo already uses `@container`: `pages-assets.css:22-24, 52-55`). 268 is arithmetic, conservative: "999 picked" (~66px) + Move to... (~72) + Delete (~48) + Clear (~42) + 3 gaps of 4 + 18px padding = ~258 plus margin; in the two-line form line 1 is the count alone and line 2 the three buttons (~170px, fits the 201px of the narrowest column). The implementer may check the widths with a `playwright-core` page on a static harness that loads the built CSS (`npm run build`, then `dist/assets/*.css`), but needs no running app; T5's case 8 proves both sides in a real browser (one line above the threshold, two below, nothing cut at 220, height equal before and after the first pick). The slot flips while the sidebar animates its width: the person caused it, accepted. Wider columns and viewers without Delete keep today's single 32px line, byte for byte (R9).
12. **Not touched (S5):** the asset page's Delete, the kinds page, the move flow. A pick bar Delete acts on the PICKS only, never on the open asset unless it is picked.

Nothing is deleted that the dialog did not show; no id is sent twice or below a deleted parent; the `expect_*` of each root are the counts the person read (or the newer ones after a refusal they confirmed); a partial failure is reported with the right numbers and leaves exactly the failed and untried roots picked.
2. Permission: no Delete without `assets.delete`; a 403 mid-loop stops the loop and says so; no request goes out for a role that cannot.
3. Keyboard and screen reader: the bar button named, the dialog's focus rules (in, Tab wrap, Escape, back), the live text, the open-not-counted sentence.
4. The open row versus a pick, in light, dark and the four presets at 1440, 1024 and 800; the bar at the narrowest column with a three-digit count; the tree with 2,000 assets stays responsive (the Delete button is in `PickSlot`, which already re-renders alone).
5. The docs tests and every needle that mentioned the old row look.
6. Focus after a delete and the scroll position; the page after the open asset is deleted (no 404 flash); the audit log has one `asset.deleted` row per root.
