# W7d: Appearance (light/dark mode and four theme presets per account) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every signed-in user can open an "Appearance" section in the profile panel and choose a Mode (Light, Dark, Match my device) and a Theme colour (Navy and gold, Maroon and gold, Graphite, Desert gold). The choice is stored on the account (migration 0007), follows the user to any browser, and is applied before the first paint from a browser-side mirror so nothing flashes and the sign-in page keeps the last look used on that browser (O-16).

**Architecture:** One additive column `users.preferences JSONB NOT NULL DEFAULT '{}'` (CHECK: a JSON object). `GET /api/me`, `POST /api/login` and `POST /api/setup` answer the normalized `preferences` `{mode, theme}`; `PUT /api/me/preferences` merges a validated partial into the caller's own row under a row lock and answers the normalized whole. The front end keeps the choice in an `AppearanceProvider`, writes `data-mode` (always `light` or `dark`; `system` is resolved in the browser through `matchMedia`) and `data-theme` on `<html>`, and mirrors it in `localStorage` (`dcdash.appearance`). The tokens switch in a new unlayered stylesheet `src/themes.css` (`:root[data-theme=…]`, `:root[data-mode="dark"]`); the app's own `:root` block in `app.css` is not touched. The dashboard widgets and the editor grid stay light cards in dark mode (a recorded limit; their restyle is the separate widgets session).

**Tech Stack:** FastAPI + SQLAlchemy async + Alembic (pytest with a Timescale test container), React 19, react-router 7, TanStack Query 5, plain CSS, ECharts 5, @xyflow/react 12, Vitest + Testing Library, Playwright (controller only).

## Decisions taken here (defaults the owner may overrule; none blocks the build)

1. **Defaults:** `mode = light`, `theme = navy-gold`. A stored `{}` means both defaults. Light is the default because "Match my device" would turn a colleague's screen dark overnight. The default look changes in one way: the navy panels get GOLD markers, focus rings and brand mark (the owner's "navy and gold = default", the roadmap's "today's navy panels with gold markers"). `app.css`'s `:root` keeps today's blue markers (`side-accent #8fb2ff`) and is the base the presets override.
2. **Server contract.** Constants in a new `backend/dcdash/core/preferences.py`: `MODES = ("light","dark","system")`, `THEMES = ("navy-gold","maroon-gold","graphite","desert-gold")`, `DEFAULTS = {"mode":"light","theme":"navy-gold"}`, `normalize(stored) -> dict` (anything that is not an object, any unknown key, any value that is not `isinstance(value, str) and value in MODES/THEMES` becomes the default for that key, checked by type BEFORE membership so a stored list or dict cannot raise; always returns exactly the two keys). `UserOut` gains `preferences` built through `normalize` (a `field_validator(..., mode="before")`), so `/api/me`, `/api/login` and `/api/setup` all carry it. `PUT /api/me/preferences` (any signed-in user, own row only): body `PreferencesIn` with `extra="forbid"` and two fields that are NOT optional types: `mode: Literal["light","dark","system"] = None  # type: ignore[assignment]` and the same for `theme` (so a JSON `null` is a 422; the natural `Literal[...] | None = None` stores a JSON null and then answers 500); a `model_validator` refuses the empty body by reading `model_fields_set` (`{}` is 422); the route uses `body.model_dump(exclude_unset=True)`. In one transaction: lock the caller's row with `locked = (await db.execute(select(User).where(User.id == user.id).with_for_update().execution_options(populate_existing=True))).scalar_one_or_none()`; when `locked is None` (the account was deleted after authentication) roll back and raise `HTTPException(401, "not authenticated")`. Do NOT use `db.refresh(user, with_for_update=True)`: on a deleted row it raises `InvalidRequestError`, which `account_vanished_is_401` does not translate (a 500 and a journal row). Keep `account_vanished_is_401` around the write and the commit anyway. Then `merged = {**normalize(locked.preferences), **given}`, write `merged` (so unknown stored keys are dropped), commit, answer `merged`. Two concurrent PUTs of different keys keep both.
3. **Audit:** exempt, like the layout save and logout: add `"PUT /api/me/preferences": "a personal display setting of the signed-in account (mode and theme), not configuration; it changes nothing another user or the system can see"` to `EXEMPT` in `tests/test_audit_coverage.py`. No audit row is written (a test asserts the count).
4. **`system` is resolved in the browser.** `<html data-mode>` is only ever `light` or `dark`; `theme-init.js` and the provider resolve `system` from `matchMedia("(prefers-color-scheme: dark)")` and, while the stored mode is `system`, re-resolve when the device preference changes. So the dark token block exists ONCE in CSS.
5. **No flash:** `frontend/public/theme-init.js` (an EXTERNAL script, because the CSP is `script-src 'self'`; Vite copies `public/` to the site root) is loaded synchronously in `<head>` of `index.html` before the module script. It reads `localStorage["dcdash.appearance"]` (JSON `{"mode","theme"}`), validates both values against its own lists (anything else = default), resolves `system`, sets the two attributes. `index.html` also carries `data-mode="light" data-theme="navy-gold"` so a failed script still gives the default. The mirror is written whenever the choice changes and when the signed-in user's preferences arrive; sign-out keeps it (the sign-in page shows the last look used on this browser); another user signing in replaces it with theirs.
6. **Provider rules:** `AppearanceProvider` sits inside `AuthProvider` and above the router. It starts from `readMirror() ?? DEFAULT_APPEARANCE` (exactly what `theme-init.js` painted) and does NOT write the attributes or the mirror on mount. While `user` is null it keeps the current look and leaves the mirror untouched (`null` is never "adopt the defaults", so the sign-in page keeps the last look). It adopts only a non-null user object that differs (by identity, the object `replaceUser` set) from the last one adopted, not on a role re-check. The `matchMedia("(prefers-color-scheme: dark)")` listener depends on the current mode only (so "Match my device" also follows the device on the sign-in page) and is removed in the effect's cleanup (StrictMode mounts twice). The context has a safe default (no provider = light, navy-gold, no-op setters) so existing tests that render a component alone keep working. A choice applies and mirrors at once (optimistic), then is saved through ONE queue: at most one PUT in flight; a choice made while one is out only updates the wanted value, and when the PUT settles the provider sends one more PUT if the wanted value differs from what the server confirmed (so the server always ends at the last choice, even when the arrow keys on a radio group send three choices in a row). A PUT carries only the keys that differ from the confirmed value. On success the server's answer (the merged whole) becomes the confirmed value and is also applied unless a newer choice is waiting. On failure the confirmed value is re-applied and mirrored (unless a newer choice is waiting) and `role="alert"` text shows in the panel ("Not saved. Check the connection and try again."). Adopting a different user (sign-in, setup) discards the queue and anything in flight (their answers are ignored) and sets confirmed = applied = that user's preferences.
7. **Presets are token overrides only** (colours of the top bar and the sidebar, the tooltip, the avatar, the find field; the content accent stays blue in every preset). Starting values are in the table below (from the designer's contrast-checked sheet, renamed to the real token names); a value that fails its pair test may be nudged, and the commit body lists every nudge.
8. **Dark mode covers the whole app except the widgets.** The island (`.widget-frame`, `.widget-preview`) re-pins the light content tokens and `color-scheme: light` in `themes.css` (unlayered), so a `.muted`, link or native button inside a white widget keeps today's contrast; `app.css`'s frozen block is not edited. The Billing muted cell (`table.billing td.muted`, frozen literals `#666` on `#f4f4f4`) gets a dark override in `themes.css` that reads 4.5:1. `color-scheme: dark` on the root makes scrollbars, date pickers and selects dark. The Trend chart takes dark colours through a parameter; the Discovery graph gets React Flow's `colorMode`. The widgets' own ECharts stay as they are.
9. **UI:** inside the existing profile panel (a disclosure, not an ARIA menu), under the name block and above Password: `<fieldset>` "Mode" with three native radios (Light, Dark, Match my device) and `<fieldset>` "Theme colour" with four native radios; each theme row shows a small decorative swatch (`aria-hidden`, the panel colour with the marker colour as a dot) and the name; the checked row is marked by the radio itself and a ring on the swatch, never by colour alone. Choosing a radio never closes the panel (arrow-key selection must work); the error line sits under the Theme colour group and clears on the next successful save; the panel shows no visible "Appearance" text or heading (the two legends are enough; a heading inside the top bar would add a heading level to every page). Each row is `<label className="prof-opt check">` (the `check` class opts it out of the layer's radio-label grid rule, which would otherwise put the swatch and the name on two lines). Radios are reached with Tab and changed with the arrow keys natively; the panel's own ArrowUp/ArrowDown walk (trigger, Password, Sign out) ignores events that start on a radio. Esc closes and returns focus to the trigger, as today. The panel grows from 240 to 264 px.
10. **Process:** lighter process with extra care where it earns it. ONE Opus plan review that runs the risky parts (below), implementer + targeted tests per task, a short Opus review of Task 1 (migration and the first self-service write on `users`), none for the other tasks, the migration rehearsal by the controller, full suites and the whole Playwright suite once at the end, ONE whole-wave Opus review that looks at the pages in a real browser in both modes and all four presets and uses the keyboard, one fix wave, one scoped re-review.
