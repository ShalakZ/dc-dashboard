# W8e Update Script Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One safe command that updates an install: `scripts\update.ps1` on Windows (and its twin `scripts/update.sh`). It checks the machine, shows where the install is and what is coming, backs up (and stops if the backup fails), fast-forwards the code, builds with the build id so Settings shows the commit, waits for the stack, verifies the database revision and the web, and ends with a plain summary and the way back. It never runs a destructive command.

**Architecture:** Scripts, tests and docs only. No application code, no migration, no UI. `scripts/update.ps1` (Windows PowerShell 5.1, ASCII only) is the main deliverable, tested from WSL through `powershell.exe` with a fake `docker.cmd`, the real Windows `git.exe` and a local bare repository as `origin`. `scripts/update.sh` has the same steps, flags and exit codes, tested with a fake `docker` and the real `git`. A real drill (controller, not an implementer) runs `update.ps1` on a copy of an older commit in the scratch Compose project `dcdash_drill_w8e`.

**Tech Stack:** PowerShell 5.1, bash, git, Docker Compose v2, pytest.

**Spec:** `.superpowers/sdd/overnight-w7/W8e-update-script.md` (the owner's request and the behaviour list). Models: `scripts/setup.ps1` (build id, `$SessionVars`, native stderr rules), `scripts/backup.ps1` (exit codes, `-CopyTo`), `scripts/check_web.sh` (the web checks), `docs/superpowers/plans/2026-10-12-w8c-field-polish.md` (a scripts wave tested from WSL).

## Decisions (rulings of the controller; each says what it costs if wrong)

1. **Build id = the commands `setup.ps1` uses**, `git describe --always --dirty` and `git log -1 --format=%cI` (the commit's own time), not "the clock of this run". The brief said UTC now; the README says the build time is the commit's, and a clock-time label would recreate `api`, `collector` and `simulator` on every update and every later `setup` run. The tree is refused when dirty, so the id is the short commit. Cost if wrong: Settings shows a tag-style id if the repo ever gets tags (same as `setup.ps1`).
2. **`docker compose build` and `docker compose up -d` are two calls, not `up -d --build`.** A failed build then provably changes nothing (the old containers still run) and exits 4 with that sentence; and an `up -d` that exits non-zero only because a long migration outlasted the api healthcheck (README step 4) is not mistaken for a failed build. Cost if wrong: none; the same two steps `up --build` does.
3. **`git merge --ff-only origin/<branch>` after the `git fetch`, not a second network call `git pull --ff-only`.** The person confirmed exactly the commits listed; a commit pushed in between is not applied silently. Messages say "updating the code". A `HEAD` that is not an ancestor of `origin/<branch>` while commits are incoming is refused at step 3 (before the question and the backup); the merge itself failing is still handled (exit 3).
4. **"Already up to date" = nothing incoming AND the running `api` container carries the same build id as the checked-out commit.** Otherwise it rebuilds even with nothing incoming ("the code is current but the site runs build X": someone pulled by hand and never rebuilt, which is exactly the owner's three-command habit). `-Force` rebuilds regardless. The running build id is read inside the container (`docker compose exec -T api printenv DCDASH_BUILD_ID`); `GET /api/version` needs a login, so it cannot be used. Cost if wrong: one extra backup and an idempotent build.
5. **Verification includes "the running api carries the id we just built".** If the build failed or `up` did nothing, the OLD healthy container would pass a health check and the revision check; so after the wait the build id inside `api` must equal the expected one (exit 4 if not).
6. **`-NoPull` means: no fetch, no branch check (a detached HEAD from a manual checkout is fine), no "incoming" list; it still backs up, builds what is checked out and verifies.** Used by the drill and by people who check out a commit.
7. **Backup exit 5 (made locally, not copied) is a stop (script exit 2)** with the local file named and the advice to fix the copy folder or run without `-CopyTo`. Safer than updating on a backup the person thought was copied. Cost if wrong: one extra run.
8. **`-Yes` skips only the question; `-DryRun` does the read-only steps** (checks, "where you are", `git fetch`, the incoming list) **and prints every command it would run for the rest; it asks nothing and changes nothing but the remote-tracking refs `git fetch` updates.** Declining the question, or an empty answer, ends with exit 1 "stopped at your request, nothing was changed".
9. **Nothing installed yet is a preflight refusal**: no containers and no `dbdata` volume for the project means "run scripts\setup.ps1 first" (exit 1). Otherwise "start only the database" would create an empty database and "back it up".
10. **Waiting.** After `up -d` the script polls every 5 s, up to 10 minutes (printed at the start), for: the `api` container running and healthy (read with `docker inspect`, so it does not depend on the `compose ps --format` JSON shape). `unhealthy` is NOT terminal while the container runs (README: a long migration can outlast the healthcheck); terminal failures are the `api` container `exited`/`dead`, or its `RestartCount` rising by 3 or more (a failed migration restarts forever under `restart: unless-stopped`). When `up -d` itself exited non-zero (web and collector were not started because `api` was not healthy yet), one more `docker compose up -d` (no build) runs once `api` is healthy. Then the `web` container healthy, then the web checks.
11. **Web checks from the host, through the published port** (`docker compose port web 80`), four lines like README step 5 (`index`, `spa fallback`, `api proxy`, `stream route`; the same assertions as `scripts/check_web.sh`'s first four). A 301/302/307/308 whose Location starts with `https://` means TLS mode: the checks are skipped with one plain sentence (the certificate is not the script's business) and the `web` container health stands in. Cost if wrong: TLS installs get fewer ok lines.
12. **Revision check:** `alembic current` and `alembic heads` run in the new `api` container; the first revision token of each must be equal (an empty `current` is a mismatch). Parsed only from lines that are a bare revision with an optional `(head)`, so INFO lines on stderr are ignored. Mismatch = exit 5.
13. **Free disk: 5 GB on the drive of the install folder** (refuse below; the dump and the build cache are the only growth). The brief said about 10; Docker's own disk cannot be read reliably from a script. A UNC path or an unreadable drive only warns. `DCDASH_UPDATE_MIN_FREE_GB` (documented in the script header) overrides the number; the tests use it to force a refusal.
14. **One update at a time:** `logs\.update.lock`, held open with no sharing for the whole run (bash: an atomic `mkdir` lock directory removed on exit). A second run refuses (exit 1).
15. **Log:** every line shown is also appended to `logs\update-<yyyyMMdd-HHmmss>.log` (the W8c convention; `logs/` is git-ignored). A log that cannot be written is a warning, never a stop. Docker's own output is streamed to the screen and the log through a helper, line by line.
16. **`update.sh` too.** `update.ps1` is the deliverable the owner asked for; `update.sh` follows in Task 3 from the reviewed PowerShell script. Its body lives in a `main()` function called as `main "$@"; exit $?` on one line, so that the `git merge` of this very step rewriting `update.sh` cannot corrupt the running shell (bash reads a script as it goes; PowerShell parses the whole file first). Cost if wrong: if Task 3 proves large, it moves to the backlog and the README says so.
17. **Exit codes (README documents them):** 0 done or already current (also `-DryRun` finished); 1 a check refused or the person said no, or bad arguments, or another update is running; 2 the backup failed or was not copied; 3 the new code could not be fetched or applied (fetch failed, not a fast-forward, merge failed); 4 the build failed, or the stack did not start, become healthy or answer, or runs the wrong build; 5 the database revision does not match the new code. An unexpected PowerShell/shell error maps to the exit code of the step it happened in and prints the step.

These same checks run on the up-to-date path (A1).
- **A5 (M3) Three failure texts, each pinned by a test.** (a) *Build failed:* the old stack and schema are untouched, the code is at the new commit; advice = fix the cause and run update again (it rebuilds); NOT the going-back pointer. (b) *Not healthy within the wait* (api still running): the migration may still be running; tell the person NOT to restore or go back yet, to watch `docker compose logs -f api` and run update again afterwards. (c) *api keeps restarting / exited:* collection is stopped, `restart: unless-stopped` keeps retrying the migration; the non-destructive way to stop it is `docker compose stop api collector`; the going-back pointer with the anchors of A3 follows. ## Global Constraints

- `scripts/update.ps1`: Windows PowerShell 5.1 compatible, **pure ASCII**, no `&&` `||` `??` `?.`, no ternary, no `-Parallel`, no `Out-File`; files written with `[IO.File]` calls and a `UTF8Encoding $false`. Follow the conventions of `setup.ps1` and `backup.ps1` (`$ErrorActionPreference = "Stop"`, `Set-Location (Join-Path $PSScriptRoot "..")`, `[Console]::Error.WriteLine` for refusals, no `2>$null` on native commands under `Stop`). Native commands are run through one helper that lowers `$ErrorActionPreference` to `Continue` around the call, folds stderr into the stream as plain text (`"$_"`, never the ErrorRecord decoration), tees every line to the screen and the log, and returns the exit code. Check `$LASTEXITCODE` after every native call.
- Parameters: `-Branch` (default `main`; must match `^[A-Za-z0-9._][A-Za-z0-9._/-]*$`), `-CopyTo`, `-NoPull`, `-Yes`, `-DryRun`, `-Force`. Anything else (including a bash-style `--yes`) prints the usage line and exits 1.
- **Never, in any path, automatically** run: `docker compose down`, `rm`, `kill`, `restart`, `docker volume ...`, `docker system|image|container prune`, `docker compose up --force-recreate|--remove-orphans|-V`, `scripts\restore.ps1`/`restore.sh`, `alembic downgrade`, `git reset|clean|checkout|stash|rebase|pull` (the code moves only by `git merge --ff-only`), or delete a dump or any file under `backups\`. A static test reads the script's non-comment lines for these tokens; a runtime test reads the fake docker's call log.
- The caller's environment is left as it was: `DCDASH_BUILD_ID`, `DCDASH_BUILD_TIME`, `BUILDX_NO_DEFAULT_ATTESTATIONS` are saved, set for the build and `up`, and restored in a `finally` (as `setup.ps1` does with `$SessionVars`). The shell twin uses a subshell or saves and unsets.
- Tests use fresh folders under the Windows temp folder, a fake `docker.cmd` first on PATH (the real Docker is never called), the **real Windows `git.exe`** with a bare repository as `origin` (so fast-forward, divergence and fetch failure are real git behaviour), and set variables INSIDE PowerShell or by cmd `set` lines (variables set in WSL do not reach `powershell.exe`; see memory note `wsl-to-powershell-drill-env`). Skipped when `powershell.exe` or `git.exe` is absent.
- No change under `frontend/` or `backend/dcdash/`: `git diff main --stat -- frontend backend/dcdash` is empty at the end. Commit trailer `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`. One commit per task, `git add` named files only.

## Review Focus

1. **It cannot lose data.** No path runs a destructive command; a failed or uncopied backup stops everything before the merge and the build; `--ff-only` never merges; a dirty tree, a wrong branch, a merge in progress, a missing `.env`, a never-installed project are refused; `-DryRun` changes nothing.
2. **It cannot report success on the old stack.** A failed build, an `up` that did nothing, a healthy OLD api, a revision that differs from the code's head, a web that answers 500: each ends non-zero with a message that says what is running.
3. **The messages are plain.** A person who is not a developer learns what was backed up and where, which commit and revision they were on, and how to go back (README "Upgrading and going back", step 6, with the commit and revision repeated).
4. **The build id and time reach the images; the caller's variables survive** (including when the script fails or is stopped).
5. **PowerShell 5.1 and the shell twin behave the same**: paths with spaces, the OneDrive warning, the exit codes the README documents are the ones returned, and every command the README now names exists.
6. **The script can replace itself**: after the merge `update.ps1`/`update.sh` on disk are the new ones; the run in progress must finish correctly (bash: the `main "$@"; exit $?` pattern, tested).

## The script's contract (what Task 1 builds; the tests pin the quoted strings)

Output starts with `DC Dashboard update`, then `Compose project: <name>` (from `docker compose config --no-interpolate`, `unknown` if it cannot say) and `Log: <path>`. Seven numbered steps, each introduced by a line `== N/7 <title> ==`; a refusal prints `REFUSED: <reason>`, `Fix: <what to do>` and, when nothing was touched, `Nothing was changed.`; the end is `DONE` or `FAILED (exit N)`.

1. **`== 1/7 Checking this computer ==`** (exit 1 on any refusal). Arguments; `git` and `docker` on PATH; inside a git work tree; `docker info` answers; `docker compose version` answers; `.env` exists and has `DCDASH_DB_PASSWORD=` with a value; the installed project exists (decision 9); no tracked modification (`git status --porcelain --untracked-files=no`; list the files); the branch is `-Branch` (skipped with `-NoPull`; a detached HEAD says so); no merge, rebase or cherry-pick in progress (`git rev-parse --git-path MERGE_HEAD` etc.); free disk (decision 13); the lock (decision 14); the OneDrive warning (same text and test as `setup.ps1`, a warning only).
2. **`== 2/7 Where you are now ==`**: `Commit: <short> <date> <subject>`, `Branch: <name or detached>`, `Database revision: <rev>` from `docker compose exec -T api alembic current` or `not running`, `Running build: <id>` from decision 4 or `not running`. Detect the simulator: `docker compose --profile dev ps -a -q simulator` non-empty adds `--profile dev` to every later compose call and says so.
3. **`== 3/7 What is coming ==`**: with `-NoPull` one line and nothing else. Otherwise `git fetch origin` (failure: exit 3), the incoming commits `HEAD..origin/<branch>` (count and the first 30 subjects, `... and N more`), the new migration files (`git diff --name-only HEAD..origin/<branch> -- backend/migrations/versions`) with the sentence `This update changes the database: the backup is taken first, and going back needs both the dump and the commit shown above.`, and a pointer to the release notes (`CHANGELOG.md` when `origin/<branch>` has it, else `README.md, section "Release notes"`). Nothing incoming and decision 4 says current: `Already up to date at <commit>` and exit 0 (`-Force` goes on). Diverged: exit 3 with the explanation. Unless `-Yes` or `-DryRun`: `Continue? (y/N)` (only `y` or `yes`, any case, continues; stdin closed counts as no).
4. **`== 4/7 Backing up the database ==`**: when the `db` container is not running, `docker compose up -d db` and wait for it healthy (up to 2 minutes). Run `backup.ps1` as a child process of the same PowerShell host (`(Get-Process -Id $PID).Path -NoProfile -ExecutionPolicy Bypass -File scripts\backup.ps1 [-CopyTo X]`) so that its exit code and its stderr reach the log. Success needs exit 0, the line `wrote <path> (schema <rev>)`, and both `<path>` and `<path>.version` existing; print `Backup written: <path> (schema <rev>)`. That schema is the "old revision" of the summary. Any failure: exit 2 (decision 7), nothing else touched.
5. **`== 5/7 Getting the new code ==`**: `git merge --ff-only origin/<branch>` (skipped with `-NoPull`, and when nothing is incoming); failure: exit 3, `The code was not changed` (verify with `git rev-parse HEAD` equal to the old one before saying so).
6. **`== 6/7 Building and starting ==`**: set the three variables (decision 1), `docker compose [--profile dev] build` (exit 4 "the running site was not touched" on failure), then `up -d`, then the wait of decision 10, printing a dot per poll and a line with the elapsed time every minute, and the sentence that the site is unavailable while the database is migrated and that readings are not collected meanwhile.
7. **`== 7/7 Checking ==`**: the running build id equals the expected one (decision 5); `alembic current` equals `alembic heads` (decision 12, exit 5); the four web lines (decision 11) as `ok: index`, `ok: spa fallback`, `ok: api proxy`, `ok: stream route`.

**Summary** (also on `-NoPull`): `Commit: <old> -> <new>`, `Database revision: <old> -> <new>`, `Backup: <path>`, `Settings now shows version: <build id>`, `To go back: README, "Upgrading and going back", step 6. You need commit <old> and revision <old>, and the backup above.`, `Log: <path>`.

**On failure after step 4** (exit 4 or 5): print what was done, the backup path, `docker compose ps`, `docker compose logs --tail 80 api`, the going-back pointer with the old commit and revision, and `Nothing further was changed. The data is safe in the backup above.`; no further docker call that changes anything.
