**Goal:** An editor selects one or many assets in the Assets Tree (click, Ctrl/Cmd-click, Shift-click ranges, keyboard) and moves them by dragging onto a row (inside, before or after it) or through a "Move to..." dialog. ## Facts checked in the code (LESSONS A12: the brief is not law)

- `PATCH /api/assets/{id}` already moves ONE asset (`parent_id` null = top level, cycle check only, name clash check `require_free_name`, which takes the advisory lock `ASSET_NAMES_LOCK` AFTER the cycle check). No batch, no sibling renumbering, no billing warning. A top-level drop is therefore allowed today.
- Sibling order everywhere is `(sort_order, name, id)` compared by code point (`core/tree.py::_order`, `lib/tree.ts::compare`). Most siblings have `sort_order` 0 and sort by name, so "before X" needs explicit numbers: the target parent's children are renumbered `0..n-1` in the new order; the old parent's remaining children keep their numbers.
- Billing reads the LIVE tree on every request and stores nothing per hierarchy (`AssetTree.load` in `api/billing.py`, `core/energy.py`, `core/cost.py`). `rate_at(tariffs, tree, asset, day)` = the nearest ancestor-or-self with a tariff row in effect on that day, else the site default (row `asset_id` NULL), else None. So a move (1) changes which override applies to the moved subtree for EVERY past day, not only from today, (2) moves the asset's kWh and cost out of the old ancestors' sums and into the new ancestors' (both branches' totals change even when no rate changes), (3) rewrites nothing: dashboards, mappings, points and tariffs refer to asset ids, which do not change; quick find, breadcrumbs, the tariff table's `asset_path` and the audit `refs` are computed from the live tree.
- Audit: `core/audit.py::audit_change(..., always=True)` writes `{**subject, before, after}`; `api/audit.py::REF_KEYS` resolves `asset_id` and `parent_id` found at the top of the detail or one level inside `before`/`after` to CURRENT names (`refs`). A new action needs: `frontend/src/lib/auditText.ts` RULES entry (`backend/tests/test_audit_describers.py` fails without it), `auditKind.ts` (+ test), `test_audit_coverage.py`, README "Audited:" list.
- The tree today is `ul.tree > li > div.node (twisty button, icon, <Link>, kind, + button)`: NOT `role=tree`. Toasts (`components/Toasts.tsx`) have no action button. `useConfirm` takes a string message. `Modal`, `Drawer`, `SaveButton`, `Skeleton` exist.

## Decisions taken here (the brief stands; these refine it; the owner may overrule any)

1. **Markup and ARIA: keep the list of links; no `role=tree`.** Rows hold real buttons (twisty, +) and a link; a `treeitem` with nested controls is poorly supported, and a real tree widget (roving tabindex, arrow-key model) would rewrite the Tab behaviour 8 e2e specs rely on (the `Skip the tree` link, link lookups by role). The multi-selection is called **picked** everywhere in code (`data-picked`, `picked`, `pick*`), NEVER "selected": `.node.is-selected`/`selectedId` already mean "the asset in the URL" (review M3). Picked is exposed by: `data-picked="true"` on the row plus `aria-describedby` on the link pointing at a visually hidden `<span class="sr-only">picked</span>` (a screen reader reads a described link; the link's accessible NAME stays the asset name, so every `getByRole("link", { name, exact: true })` keeps working; review M10), the picked bar (a `role="group"` named "Selection", "N picked"), and ONE role-less `aria-live="polite"` line in the tree ("Pump 3 picked, 2 picked in all"; once, the first time something is picked: "Press M to move"). Keyboard on a focused row link: Space toggles (a link does not use Space), ArrowUp/ArrowDown move focus to the previous/next VISIBLE row link, Shift+ArrowUp/Down extend the range from the anchor, **`M` (and Shift+F10 / the context-menu key) opens Move to... for the picked rows, or for that row when none is picked** (review I9: the bar is otherwise thousands of Tab stops away), Escape (while the picked set is non-empty) clears it, Enter opens (native). Cost if wrong: a screen-reader user may want `aria-multiselectable`; Move to... (bar, `M`) covers the same work.
2. **The picked bar is a RESERVED slot at the TOP of the tree column**, below the filter and above the rows, as the brief says (review: judged; a slot that is always drawn shifts nothing). For editors it is always there, one fixed 32 px line: with nothing picked it shows the muted hint "Ctrl-click to pick several" (truncated with an ellipsis when room is short) and, WHEN AN ASSET IS OPEN, a button "Move to..." (title "Move <name> to another place") that moves that open asset: this is the touch and one-asset route WITH the rate warning (review I8 asked for a route with the warning; a header button was rejected for the pinned header layout, so the route lives in the slot that already exists); with picks it shows "N picked", "Move to..." and "Clear". Without `assets.edit` the slot does not exist. Cost if wrong: 32 px less room for rows in the tree column.
3. **Click rules.** Plain click on a row link: opens the asset (as today) and clears the picked set. Ctrl click (Cmd on a Mac; on a Mac Ctrl-click is a right click and gives no `click`, so only Cmd toggles there): `preventDefault`, toggles the row, does not open it. Shift click: `preventDefault` on `mousedown` too (it would extend a text selection across the rows), picks every visible row between the anchor and the clicked row in tree order (rows hidden by a fold or a filter excluded), replacing the previous picks, anchor unchanged. react-router's `Link` runs the caller's `onClick` first and navigates only if it did not `preventDefault`. Without `assets.edit` none of this exists (the link behaves natively, Ctrl-click opens a new tab). For editors Ctrl-click no longer opens a new tab (middle click and the context menu still do). The picked set is local to `AssetTree`, pruned when an id leaves the asset list, cleared after a successful move.
4. **Normalising.** The server and the client both reduce the ids to ROOTS (an id with an ancestor in the set travels inside that ancestor), ordered by the tree order BEFORE the move, not the order sent.
5. **Drop zones** (pure function `dropZone(rectTop, rectHeight, y, expandedWithKids)`): top 25% = before the row (sibling of the row), middle 50% = inside (last child), bottom 25% = after the row (sibling) EXCEPT when the row is expanded and has visible children, where the bottom 25% = inside as FIRST child (`before_id` = its first child). A filler `div.tree-root-drop` below the last row (flex-grow, always present for editors, so nothing shifts; it sits OUTSIDE `ul.tree` and has its own drag handlers) = top level, last. Hover on a collapsed row's middle for 600 ms expands it. **`before_id` rule (review I4), in `resolveDrop` and mirrored by the server:** `before_id` = the first sibling at or after the computed position that is NOT in the moved set (null if none), computed on the UNFILTERED tree (a filter hides siblings; "after R" still means after R among ALL of R's siblings). Siblings A B C D with A and C dragged after B give `before_id` D; dragging an expanded row's first child onto its bottom edge gives the NEXT child. The SERVER is also tolerant: a `before_id` that is a currently-moved root under the target is skipped forward to the next non-moved sibling; only a `before_id` that is not a child of the target (or gone) is refused.
6. **Native HTML5 drag and drop**, with event delegation on `ul.tree` (one `dragover` handler: `closest("[data-asset-id]")`). `draggable="true"` is on `div.node` and `draggable="false"` on the inner `<a>` and the buttons (so a link is not dragged as a URL). `dragstart` calls `dataTransfer.setData("text/plain", <names>)` (Firefox starts no drag without data) and sets `effectAllowed = "move"`; every accepted `dragover` sets `dropEffect = "move"` and calls `preventDefault` (Windows maps Ctrl+drag to copy: an e2e case drags with Ctrl held). The drop marker, the invalid mark and the hover mark are DIRECT DOM writes of `data-drop="before|inside|after|invalid"` on the row (NEVER `classList`: React rewrites `className`), only when the (row, zone) pair changes, so a `dragover` causes no React render; they are cleared on `drop`, `dragend` and when the pointer leaves the tree, so a refetched row keeps no stale marker. `setDragImage` shows a small badge ("3 assets", or the asset's name for one) built as a throw-away element that is removed again at once (it must not leave a `.node` in the DOM: `w7e.spec.ts:510` counts them). Dragging a picked row drags the whole picked set; dragging an unpicked row drags just that row and leaves the picks alone. Auto-scroll: try Chromium's native drag autoscroll first; add an rAF loop (within 32 px of the scroll box's top/bottom edge) only if the e2e/look shows it does not scroll, and never both (two scrollers fight). Escape cancels (native). Touch has no native drag: the dialog is the touch route.
7. **Server API (the contract all tasks share).**
   - `POST /api/assets/move-preview` and `POST /api/assets/move`, both `assets.edit` (no new permission; `ROUTE_PERMISSIONS` and the coverage gate get both). Body `MoveIn`:
     `{ "moves": [ { "ids": [int,...], "parent_id": int|null, "before_id": int|null } ], "expect": { "assets"?: int, "parents"?: { "<id>": int|null }, "rate_changes"?: bool } | null, "undo_of"?: string|null }`.
     1 to 500 groups, at most 500 ids in all (an undo of 500 roots may need 500 groups), each id at most once across the request (422 otherwise). `before_id` null = last child of `parent_id` (or last root).
   - Groups are applied in order to an in-memory copy of the tree; a later group sees the earlier ones. All checks run before any write: ONE refusal moves nothing (atomic).
   - **The decision function** `decide(tree, group, rules=RULES) -> list[Refusal]` in the new `backend/dcdash/core/tree_move.py` (pure, no database), `Refusal(asset_id, code, reason)` with `reason` a full sentence in names. Built-in checks: ids exist (else stale), target exists, an id into itself or into its own descendant (`cycle`), `before_id` is a child of the target (`bad_before`; a `before_id` that is a currently-moved root under the target is skipped forward, see decision 5), a sibling name clash (`name_clash`: against the target's children that stay AND against another root of the same group; compared with the SAME SQL normalisation as `asset_names._KEY`, fetched from the database, not re-implemented; **a pure reorder inside the same parent skips the clash check**, as `update_asset` does at `assets.py:157`: old twins stay reorderable), nothing to do (`unchanged`: soft, defined as "same parent AND the target's final child sequence equals the current one"; the id is skipped and listed in `unchanged`; if every id of a request is unchanged the route answers 422 "already there"). `RULES: list[Callable]` is empty: per-kind rules (a later wave) append here and need no route change. For an `undo_of` request a `before_id` that is no longer a child of the target falls back to LAST instead of refusing (the `expect.parents` guard the real conflict).
   - Status codes: rule refusals 422 `{"detail": "<first reason>", "refusals": [{id, name, reason, code}]}`; stale (an id or target gone, `expect` mismatch, a locked row no longer there) 409 `{"detail": "...", "stale": true}`; permission 403 as everywhere.
   - **`expect`** (the W7k pattern, all optional): `assets` = the number of assets that move in all (roots plus descendants, `unchanged` ids not counted); the real count ABOVE it refuses (a child was added under a moved asset since the preview). `parents` = each ROOT's parent as shown; any difference refuses (someone else moved it), and so does a real set of roots that differs from the keys (a picked child moved out from under a picked parent since the preview). `rate_changes` = what the preview said; the move computes the rates itself (the same function as the preview) and refuses (409 stale, "a rate changed since you looked") when it finds a rate change and the caller said `false` (a tariff added between the preview and the move must not slip past the warning). The preview returns the `expect` to send back; an API caller may omit it.
   - **Preview response** (200, no side effects, no audit, takes no locks): `{ "assets": N, "unchanged": [id], "currency": "USD", "rate_changes": bool, "roots": [ { "id", "name", "subtree_assets", "from_parent_id", "from_parent_name", "to_parent_id", "to_parent_name", "change": "parent"|"order", "rate_before": float|null, "rate_after": float|null, "rate_changes_today": bool, "rate_changes_other_days": bool } ], "expect": { "assets": N, "parents": { "<id>": parent|null }, "rate_changes": bool } }`. `currency` is the site currency from the server (the client's billing-settings hook needs `tariffs.view`, which an assets editor may lack; the per-kWh numbers are shown to every editor on purpose: the asset page shows the same person its cost already). Rates: `rate_at` on the current tree and on the planned tree for the site-local TODAY and for EVERY `effective_from` date of any tariff row, past AND future (the rate only changes at those dates, so that is exhaustive; a row entered in advance changes the billing from its date); `rate_changes_today` compares today, `rate_changes_other_days` compares the other dates; `rate_changes` = any root with either. Per ROOT only: a descendant either has an owner inside the moved subtree (its rate cannot change) or inherits the root's rate (it changes exactly when the root's does); a container whose children all carry overrides warns falsely, accepted. A pure reorder inside one parent has `change: "order"` and never a rate change.
   - **Move response** (200): `{ "request_id": "<uuid4>", "assets": N, "unchanged": [id], "moved": [ { "id", "name", "from_parent_id", "to_parent_id", "from_parent_name", "to_parent_name", "change" } ], "undo": { "moves": [group...], "expect": {assets, parents} } }`. **`undo.moves` has one group per maximal RUN of consecutive moved roots in the OLD sibling order** (A X B C with A and B moved is two runs, so X stays between them again): for each run `before_id` = the first old sibling after the run that did not move, else null; `undo.expect.parents` = where the move put them. Undo is the same route with `undo_of` = the first request's `request_id`. Positions come back "as close as the remaining siblings allow".
   - **Concurrency (review I1, I2).** Order: take `ASSET_NAMES_LOCK` (`pg_advisory_xact_lock`) as the FIRST statement, held to commit -> load the tree with COLUMN selects (no ORM instance loaded earlier can be stale) -> decide/plan in memory -> ONE locking statement `SELECT id FROM assets WHERE id IN (moved roots ∪ renumbered siblings ∪ every group's target parent_id ∪ every before_id) ORDER BY id FOR UPDATE`; any id missing gives 409 stale. FOR UPDATE on the new parent makes the foreign-key check's KEY SHARE free, so no lock is taken after this statement and there is no cycle with `delete_asset`'s subtree lock or the kinds route's row locks (the reviewer's deadlock: a delete of an ancestor of the target holds the target and waits on a child the move holds) -> write with core `update()` statements -> audit -> commit. **`update_asset` takes the same advisory lock as its FIRST statement, before `get_asset`, whenever `parent_id` or `name` is in the body** (today it loads the row, checks the cycle and only then locks, so a rename that waited behind a move would check names under the OLD parent); a rename-only PATCH that waited behind a move is checked against the new siblings (test). Two moves serialise on the advisory lock, so two admins moving overlapping sets end consistent (TWO real connections). Race tests (T1): (a) delete the GRANDPARENT of the drop target while moving into the target whose children have higher ids than it; (b) a kind delete-and-move of the target's kind against a move into the target; both end in 409 or success, never a deadlock error. No `notify(CONFIG_CHANNEL)`: no mapping changes.
   - **Audit.** One `asset.moved` row per moved ROOT (and per reordered root), `audit_change(..., always=True)`: subject `{asset_id, name, request_id, moved_with: <INT: how many OTHER roots the request moved>, subtree_assets, undo_of?}`, `before {parent_id, parent_name, sort_order}`, `after {parent_id, parent_name, sort_order}` (`parent_name` null at the top level; the names are stored too so a row still reads after the parent is deleted). `auditText` prefers `refs` (current name), falls back to the stored `parent_name`, then "a deleted asset"; `auditKind` classes `.moved` as a change. Nothing is written for `unchanged` ids or for the renumbered siblings.

## Review Focus (inputs the happy path does not exercise)

1. **No move can corrupt the tree.** A cycle is refused (also across the groups of one request and against a concurrent PATCH); a refusal in the middle of a batch moves NOTHING; two simultaneous moves of overlapping sets end consistent (two real connections); a delete racing a move gives 409, not a half move; the moved assets' descendants are intact; sibling order after a move is exactly what the marker showed (before/after/inside/first-child), also when siblings all have `sort_order` 0; a name clash with a sibling or between two moved roots is refused with both names in the reason.

4. **Keyboard and screen reader do everything the mouse does** (Space, Shift+Arrow, Escape, Move to... by keyboard, the dialog's focus return, the live line says each change once). Touch width: the dialog works, nothing is broken.
5. **Performance** on a 2,000-asset tree: drag-over stays smooth (no React render per event), a 200-row range select does not stall.
6. **Read-only roles** see no picking, no draggable rows, no top slot and no `M` key, and the API answers 403; the audit rows read in names and the drawer shows `together with N others`.
7. **Layout:** the tree header (title "Assets Tree" at 1024 with the sidebar minimised AND expanded) is not touched; the reserved top slot and the root filler cause no shift of rows (compare row positions before and after a pick at 1440/1024/800); the asset page header is NOT changed (no fourth button); toasts above the tree do not cover the Undo button's neighbours; z-order tip 1100 > dialog 1000 > toasts 900 > drawer.
