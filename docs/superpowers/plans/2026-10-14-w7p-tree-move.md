> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An editor selects one or many assets in the Assets Tree (click, Ctrl/Cmd-click, Shift-click ranges, keyboard) and moves them by dragging onto a row (inside, before or after it) or through a "Move to..." dialog. ## Facts checked in the code (LESSONS A12: the brief is not law)

- `PATCH /api/assets/{id}` already moves ONE asset (`parent_id` null = top level, cycle check only, name clash check `require_free_name`, which takes the advisory lock `ASSET_NAMES_LOCK` AFTER the cycle check). No batch, no sibling renumbering, no billing warning. A top-level drop is therefore allowed today.
- Sibling order everywhere is `(sort_order, name, id)` compared by code point (`core/tree.py::_order`, `lib/tree.ts::compare`). Most siblings have `sort_order` 0 and sort by name, so "before X" needs explicit numbers: the target parent's children are renumbered `0..n-1` in the new order; the old parent's remaining children keep their numbers.
- Billing reads the LIVE tree on every request and stores nothing per hierarchy (`AssetTree.load` in `api/billing.py`, `core/energy.py`, `core/cost.py`). `rate_at(tariffs, tree, asset, day)` = the nearest ancestor-or-self with a tariff row in effect on that day, else the site default (row `asset_id` NULL), else None. So a move (1) changes which override applies to the moved subtree for EVERY past day, not only from today, (2) moves the asset's kWh and cost out of the old ancestors' sums and into the new ancestors' (both branches' totals change even when no rate changes), (3) rewrites nothing: dashboards, mappings, points and tariffs refer to asset ids, which do not change; quick find, breadcrumbs, the tariff table's `asset_path` and the audit `refs` are computed from the live tree.
- Audit: `core/audit.py::audit_change(..., always=True)` writes `{**subject, before, after}`; `api/audit.py::REF_KEYS` resolves `asset_id` and `parent_id` found at the top of the detail or one level inside `before`/`after` to CURRENT names (`refs`). A new action needs: `frontend/src/lib/auditText.ts` RULES entry (`backend/tests/test_audit_describers.py` fails without it), `auditKind.ts` (+ test), `test_audit_coverage.py`, README "Audited:" list.
- The tree today is `ul.tree > li > div.node (twisty button, icon, <Link>, kind, + button)`: NOT `role=tree`. Toasts (`components/Toasts.tsx`) have no action button. `useConfirm` takes a string message. `Modal`, `Drawer`, `SaveButton`, `Skeleton` exist.

## Decisions taken here (the brief stands; these refine it; the owner may overrule any)

1. **Markup and ARIA: keep the list of links; no `role=tree`.** Rows hold real buttons (twisty, +) and a link; a `treeitem` with nested controls is poorly supported, and a real tree widget (roving tabindex, arrow-key model) would rewrite the Tab behaviour 8 e2e specs rely on (the `Skip the tree` link, link lookups by role). Selection is exposed by: a visually hidden `<span class="sr-only">selected</span>` as a SIBLING after the link (the link's accessible name stays the asset name, so every `getByRole("link", { name, exact: true })` keeps working), the selection bar (a `role="group"` named "Selection", "N selected"), and ONE role-less `aria-live="polite"` line in the tree that says "Pump 3 selected, 2 selected in all". Keyboard on a focused row link: Space toggles (a link does not use Space), ArrowUp/ArrowDown move focus to the previous/next VISIBLE row link, Shift+ArrowUp/Down extend the range from the anchor, Escape (while the selection is non-empty) clears it, Enter opens (native). Cost if wrong: a screen-reader user may want `aria-multiselectable`; the Move to... route (header button, selection bar) covers the same work.
2. **Selection bar at the BOTTOM of the tree column**, not the top as the brief says: a bar that appears above the rows shifts every row down while the person is mid Ctrl-click (LESSONS A2). At the bottom it only shortens the scroll box. Content: "N selected", "Move to...", "Clear". Cost if wrong: less discoverable than a top bar; the owner can flip it.
3. **Click rules.** Plain click on a row link: opens the asset (as today) and clears the selection. Ctrl or Cmd click: `preventDefault`, toggles the row, does not open it. Shift click: `preventDefault`, selects every visible row between the anchor and the clicked row in tree order (hidden children of folded nodes excluded; a filter's hidden rows excluded), replacing the previous selection, anchor unchanged. Without `assets.edit` none of this exists (the link behaves natively, Ctrl-click opens a new tab). For editors Ctrl-click no longer opens a new tab (middle click and the context menu still do). Selection is local to `AssetTree`, pruned when an id leaves the asset list, cleared after a successful move.
4. **Normalising.** The server and the client both reduce the ids to ROOTS (an id with an ancestor in the set travels inside that ancestor), ordered by the tree order BEFORE the move, not the order sent.
5. **Drop zones** (pure function `dropZone(rectTop, rectHeight, y, expandedWithKids)`): top 25% = before the row (sibling of the row), middle 50% = inside (last child), bottom 25% = after the row (sibling) EXCEPT when the row is expanded and has visible children, where the bottom 25% = inside as FIRST child (`before_id` = its first child). A filler `div.tree-root-drop` below the last row (flex-grow, always present for editors, so nothing shifts) = top level, last. Hover on a collapsed row's middle for 600 ms expands it. The scroll box scrolls (rAF loop) within 32 px of its top/bottom edge during a drag.
6. **Native HTML5 drag and drop**, with event delegation on `ul.tree` (one `dragover` handler: `closest("[data-asset-id]")`). `draggable="true"` is on `div.node` and `draggable="false"` on the inner `<a>` and the buttons (so a link is not dragged as a URL). The drop marker, the invalid mark and the hover class are set by DIRECT DOM attribute writes (`data-drop="before|inside|after|invalid"` on the row), only when the (row, zone) pair changes, so a `dragover` causes no React render. `setDragImage` shows a small badge ("3 assets", or the asset's name for one). Dragging a selected row drags the whole selection; dragging an unselected row drags just that row and leaves the selection alone. Escape cancels (native). Touch has no native drag: the dialog is the touch route.
7. **Server API (the contract all tasks share).**
   - `POST /api/assets/move-preview` and `POST /api/assets/move`, both `assets.edit` (no new permission; `ROUTE_PERMISSIONS` and the coverage gate get both). Body `MoveIn`:
     `{ "moves": [ { "ids": [int,...], "parent_id": int|null, "before_id": int|null } ], "expect": { "assets"?: int, "parents"?: { "<id>": int|null } } | null, "undo_of"?: string|null }`.
     1 to 50 groups, at most 500 ids in all, each id at most once across the request (422 otherwise). `before_id` null = last child of `parent_id` (or last root).
   - Groups are applied in order to an in-memory copy of the tree; a later group sees the earlier ones. All checks run before any write: ONE refusal moves nothing (atomic).
   - **The decision function** `decide(tree, group, rules=RULES) -> list[Refusal]` in the new `backend/dcdash/core/tree_move.py` (pure, no database), `Refusal(asset_id, code, reason)` with `reason` a full sentence in names. Built-in checks: ids exist (else stale), target exists, an id into itself or into its own descendant (`cycle`), `before_id` is a child of the target and not itself moved (`bad_before`), a sibling name clash (`name_clash`: against the target's children that stay AND against another root of the same group; compared with the SAME SQL normalisation as `asset_names._KEY`, fetched from the database, not re-implemented), nothing to do (`unchanged`: soft, the id is skipped and listed in `unchanged`; if every id of a request is unchanged the route answers 422 "already there"). `RULES: list[Callable]` is empty: per-kind rules (a later wave) append here and need no route change.
   - Status codes: rule refusals 422 `{"detail": "<first reason>", "refusals": [{id, name, reason, code}]}`; stale (an id or target gone, `expect` mismatch, a locked row no longer there) 409 `{"detail": "...", "stale": true}`; permission 403 as everywhere.
   - **`expect`** (the W7k pattern): `assets` = the number of assets that move in all (roots plus descendants); real count ABOVE it refuses (a child was added under a moved asset since the preview). `parents` = each root's parent as shown; any difference refuses (someone else moved it). The preview returns the `expect` to send back; an API caller may omit it.
   - **Preview response** (200, no side effects, no audit, takes no locks): `{ "assets": N, "unchanged": [id], "rate_changes": bool, "roots": [ { "id", "name", "subtree_assets", "from_parent_id", "from_parent_name", "to_parent_id", "to_parent_name", "change": "parent"|"order", "rate_before": float|null, "rate_after": float|null, "rate_changes_today": bool, "rate_changes_past": bool } ], "expect": { "assets": N, "parents": { "<id>": parent|null } } }`. Rates: `rate_at` on the current tree and on the planned tree for the site-local TODAY and for every `effective_from` date <= today of any tariff row (the rate only changes at those dates, so that is exhaustive); `rate_changes_today` compares today, `rate_changes_past` compares the other dates; `rate_changes` = any root with either. Per ROOT only: a descendant either has an owner inside the moved subtree (its rate cannot change) or inherits the root's rate (it changes exactly when the root's does). A pure reorder inside one parent has `change: "order"` and never a rate change.
   - **Move response** (200): `{ "request_id": "<uuid4>", "assets": N, "unchanged": [id], "moved": [ { "id", "name", "from_parent_id", "to_parent_id", "from_parent_name", "to_parent_name", "change" } ], "undo": { "moves": [group...], "expect": {assets, parents} } }`. `undo.moves` has one group per OLD parent (its roots in their old relative order, `before_id` = the first remaining old sibling that followed the group's first member, else null); `undo.expect.parents` = where the move put them. Undo is the same route with `undo_of` = the first request's id. Positions come back "as close as the remaining siblings allow".
   - **Concurrency.** Order: take `ASSET_NAMES_LOCK` (`pg_advisory_xact_lock`, held to commit; every writer of the tree's SHAPE now takes it BEFORE it reads: also `update_asset` when `parent_id` or `name` is in the body, which today checks the cycle first and locks later, a race the new route would widen) -> `AssetTree.load` -> decide/plan in memory -> `SELECT id FROM assets WHERE id IN (rows to write) ORDER BY id FOR UPDATE` (a row missing = a delete won the race: 409 stale; this keeps the order id-ascending like `delete_asset`'s subtree lock, so no deadlock with a delete) -> UPDATE -> audit -> commit. Two moves serialise on the advisory lock, so two admins moving overlapping sets end consistent (test with TWO real connections). No `notify(CONFIG_CHANNEL)`: no mapping changes.
   - **Audit.** One `asset.moved` row per moved ROOT (and per reordered root), `audit_change(..., always=True)`: subject `{asset_id, name, request_id, moved_with: <other roots in the request>, subtree_assets, undo_of?}`, `before {parent_id, sort_order}`, `after {parent_id, sort_order}` (numbers; `refs` supplies the names, "a deleted asset" when gone). Nothing is written for `unchanged` ids or for the renumbered siblings.
8. **Billing wording** (warning and README, verified above): "Past periods are recalculated at the new place, and the totals of both branches change." When no rate changes the totals still move; the README says so, the warning stays silent (the owner's rule: a warning only when a rate changes).
9. **The warning** (client): after the drop the client calls the preview. If `rate_changes` is false it sends the move at once. If true it asks `useConfirm` (`confirmLabel` "Move anyway", tone primary, title "This changes the rate", message built by `lib/moveText.ts`): one root: `Moving "Pump 3" changes its rate from 0.18 to 0.12 per kWh. Past periods are recalculated at the new place, and the totals of both branches change.`; a root whose rate changed only in the past: `... changes the rate its past periods are billed at.`; no rate on one side: `from 0.18 to no rate` (no tariff applies: its energy shows without cost); several roots: the first three names with their rates, then "and N more". Rates formatted with the site currency from the existing settings hook. Cancel moves nothing and keeps the selection.
10. **Undo toast.** `ToastApi.success(text, options?)` gains `options: { action?: { label: string; onAction: () => void }; durationMs?: number }` (T3). The move's toast: "Moved 3 assets to Row A" + button "Undo", 8 s, hover/focus hold as today. Undo sends `undo.moves` with `undo.expect`; success toast "Undone" (no second Undo); a 409 shows an error toast "Something moved since; the move could not be undone". The toast stays inside the existing live region (no second announcer).
11. **"Move to..." dialog** (`MoveDialog.tsx`, `Modal`): a search box ("Search places"), a "Top level" radio first, then every asset as a radio indented by depth, in tree order; invalid targets (the moved assets themselves, their descendants, the current parent when it is the only change, a name clash) are `aria-disabled` radios with the reason as muted text under the name. Primary button "Move" (disabled until a target is chosen), always "last child". Opened from the selection bar (selection) and from a new asset-page header button "Move to..." (the open asset; the touch route). The header gets the button between Edit and Delete; the W7o container thresholds (580/720 px) are re-measured and retuned by T5 with their tests.
12. **Performance.** `Row` becomes `React.memo`; the parent computes primitive props (`selected`, `current`, `open`, kids); the selection is a `Set` in a reducer; a range select is ONE state update. T4 measures a 2,000-asset tree once in the browser (a node script with `playwright-core` on the scratch stack: a drag-over burst, a 200-row Shift selection) and writes the numbers into its report.

## Review Focus (inputs the happy path does not exercise)

1. **No move can corrupt the tree.** A cycle is refused (also across the groups of one request and against a concurrent PATCH); a refusal in the middle of a batch moves NOTHING; two simultaneous moves of overlapping sets end consistent (two real connections); a delete racing a move gives 409, not a half move; the moved assets' descendants are intact; sibling order after a move is exactly what the marker showed (before/after/inside/first-child), also when siblings all have `sort_order` 0; a name clash with a sibling or between two moved roots is refused with both names in the reason.
2. **Billing follows the tree exactly as the warning says.** Compare `GET` billing costs of a moved asset and of both ancestor chains before and after against the preview's numbers on a real database; a rate change in the past only; no tariff on either side; the warning appears ONLY when a rate changes; a reorder inside one parent never warns.
3. **Selection feels like a file manager** and a click never opens an asset by accident while selecting (Ctrl/Cmd/Shift click do not navigate; a text selection or a drag is not a click).
4. **Keyboard and screen reader do everything the mouse does** (Space, Shift+Arrow, Escape, Move to... by keyboard, the dialog's focus return, the live line says each change once). Touch width: the dialog works, nothing is broken.
5. **Performance** on a 2,000-asset tree: drag-over stays smooth (no React render per event), a 200-row range select does not stall.
6. **Read-only roles** see no checkbox-less selection, no draggable rows, no bar, no header button, and the API answers 403; the audit rows read in names and the drawer shows `moved together with N others`.
7. **Layout:** the tree header (title "Assets Tree" at 1024 with the sidebar minimised AND expanded) is not touched; the bottom bar and the filler cause no shift of rows; the asset header at 1024/800 with four buttons; toasts above the bar do not cover Undo's neighbours; z-order tip 1100 > dialog 1000 > toasts 900 > drawer.
