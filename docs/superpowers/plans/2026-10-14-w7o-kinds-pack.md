10. **Delete-and-move** (review M1, M2, M3). `DELETE /api/asset-kinds/{kind_id}?move_to={id}&expect_assets={n}` (`assets.kinds`), 204 as today. Rules: (a) when `move_to` is given, ONE statement locks both rows in ascending id order: `SELECT ... WHERE id IN (:kind, :target) ORDER BY id FOR UPDATE` with `populate_existing` (PostgreSQL's LockRows sits above the Sort, so the rows are locked in id order; two concurrent A->B and B->A deletes cannot deadlock); without `move_to` the existing `locked_kind` path is unchanged; the SOURCE missing -> 404 `KIND_NOT_FOUND`, the TARGET missing -> 422 "That kind no longer exists." (do not reuse `locked_kind`, it answers 404); (b) `move_to` equal to `kind_id` -> 422 "Pick another kind to move the assets to." (checked before locking); (c) the live count under the lock (as `kind_counts`): if `expect_assets` is given and differs from it -> 409 `{"detail": "<N> assets use this kind now ...", "assets": N}` and nothing changes. This is the W7k stale-impact idea but STRICTER on purpose: W7k refuses only when the live count is ABOVE the expectation, this refuses on any difference, so the toast ("3 assets moved") and the audit row agree with what the dialog showed; the 422 check for a missing target comes BEFORE the stale 409; (d) count > 0 and no `move_to` -> the existing 409 ("N assets use this kind. Change their kind first.", `assets: N`); (e) otherwise ONE transaction: the spellings of the kind's key are found in Python (as the rename cascade does), their asset rows are locked `SELECT id FROM assets WHERE kind IN (:spellings) ORDER BY id FOR UPDATE` (the cheap cure for a deadlock with `delete_asset`, which locks its subtree by id), then `UPDATE assets SET kind = <target name>` for them, then the kind row is deleted, then ONE audit row `kind.deleted` `{kind_id, name, icon, assets: <the UPDATE's rowcount>, moved_to: <target name>}` (the last two keys only when rows moved; a plain delete writes exactly what it writes today); an error halfway rolls everything back (a test makes the UPDATE fail). A `move_to` with a kind nobody uses moves 0 assets and is allowed. The assets' own `icon` is untouched. **Expected result of the crossed A->B / B->A test: one 204, the other 422** (the loser waits, then its target is gone). The module docstring notes the asset-row lock.
