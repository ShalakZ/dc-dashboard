10. **Delete-and-move.** `DELETE /api/asset-kinds/{kind_id}?move_to={id}&expect_assets={n}` (`assets.kinds`). Rules: (a) the kind row is locked FIRST; when `move_to` is given the target row is locked too, and **both locks are taken in ascending id order** (two concurrent A->B and B->A deletes must not deadlock); (b) `move_to` equal to `kind_id` -> 422 "Pick another kind to move the assets to."; a target that does not exist -> 422 "That kind no longer exists."; (c) the live count under the lock (as `kind_counts`): if `expect_assets` is given and differs from it -> 409 `{"detail": "<N> assets use this kind now ...", "assets": N}` and nothing changes (this is W7k's stale-impact guard; the dialog refreshes with N); (d) count > 0 and no `move_to` -> the existing 409 ("N assets use this kind. Change their kind first.", `assets: N`); (e) otherwise ONE transaction: the spellings of the kind's key are found in Python (as the rename cascade does) and `UPDATE assets SET kind = <target name>` for them, then the kind row is deleted, then ONE audit row `kind.deleted` `{kind_id, name, icon, assets: N, moved_to: <target name>}` (the last two keys only when N > 0; a plain delete writes exactly what it writes today); an error halfway rolls everything back (a test makes the UPDATE fail). A `move_to` with a kind nobody uses moves 0 assets and is allowed. The assets' own `icon` is untouched. The response stays 204.
