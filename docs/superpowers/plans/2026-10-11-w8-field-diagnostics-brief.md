# W8 brief: field diagnostics (debugging the real SCADA connection by copy-paste)

**Why.** The owner will connect the app to the real SCADA on the workstation: Windows, reached over RDP, no internet, no Claude, nobody who can supervise live (backlog sections B and D). The only channels are text the owner copies from the RDP session and pastes into a Claude session, and files carried back over RDP drive redirection. This wave builds the framework that makes that loop work: every failure must be diagnosable from ONE pasted report, and every fix must come back as something small the owner can apply. ("We'll have to establish some sort of framework or logging I can share with you directly that I'll have to essentially copy paste back and forth." Owner, 2026-10-11.)

**Planning rule.** The controller turns this brief into a normal plan (interfaces, rules, risky code, key tests) and has it reviewed before coding. Everything below is the intent; where the code shows a better shape, rule and record it. **Merge cut:** W8 is DONE (and merged) when A, C, G, B (OPC UA; Modbus may follow), F, D and E-lite are built and gated; build in the order A, C, E-lite, G, B, F, D. Parts H, I and the rest of E are wave W8b (they run after W8 is merged); never let them block the W8 merge. **E-lite** (right after C, because it is the only piece usable on day one: the workstation has no Docker and no WSL, and the install bundle is out of scope): a standalone `scripts/collect-diagnostics.ps1` (PowerShell 5.1) that prints and saves host facts, free disk, clock, DNS and TCP reachability for host:port pairs given as arguments, with no dependency on the app.

## Parts
**A. Event journal (persistent, bounded).** A table (new migration 0006, the next free number; the theme wave O-16 then moves to 0007; rehearse the upgrade and a lossless downgrade on a restored copy of the dev DB) of diagnostic events: time, level, component (collector / api / scan / job), source id, kind, code, message, small JSON detail. Capped by age and row count (for example 14 days, 20 000 rows) by the existing housekeeping job. Written on TRANSITIONS, not on every repeat: connect attempt/success/failure with a reason class, backoff, per-point read errors aggregated (count, first/last time, last error) instead of one row per read, status-code histogram, fresh/stale/bad transitions, clock skew seen, job results (Test, Browse, Scan). It must not become a new source of log spam or disk growth, and a failing journal write must never break the collector.

**B. Connection check (step-by-step probe, runs in the collector as a job like Test/Browse).** For an OPC UA source, in order, each step OK/FAIL with milliseconds and the exact error (exception class plus OPC UA status name and hex): 1 DNS resolution; 2 TCP connect; 3 GetEndpoints (which security policies, modes and user-token types the server offers, and whether the configured combination is among them); 4 certificates (our client certificate thumbprint, subject, expiry; the server certificate subject, expiry, whether its host name matches the URL; trust state); 5 secure channel and session with the configured authentication; 6 server time (clock skew against the local clock: a skew beyond a few minutes breaks OPC UA); 7 namespace array; 8 one read of every mapped point (value, status code, source and server timestamps, data type, access level); 9 timing over about 5 reads (step 8's reads are batched in chunks of the server's MaxNodesPerRead, not one call per point). Each FAIL carries a plain-language hint from a lookup table: what the usual cause is and what to ask the SCADA or network team (clock skew has a LOCAL cause too: the Docker Desktop / WSL2 VM clock drifts after the host sleeps, so the report shows the container clock against the database clock before it blames the SCADA; for example BadSecurityChecksFailed / BadCertificateUntrusted: the server does not trust our certificate, give them thumbprint X; BadIdentityTokenRejected / BadUserAccessDenied: account or password; BadTcpEndpointUrlInvalid or a connect timeout: wrong URL/port or a firewall; BadNodeIdUnknown: wrong node id or namespace index; clock skew). Modbus: TCP connect, unit id, a test read, exception codes. The check is read-only toward the SCADA and limited: refuse to start when a pending or running check exists for the source, with a cooldown of a few seconds after one finishes (today's `POST /sources/{id}/test` has no limit and the job runner has 4 workers, so enforce it in the enqueue code); never inside a tight loop; fragile devices exist (backlog B).

**C. Report builder.** `GET /api/diagnostics/report?detail=summary|full&mask=0|1&source=<id>` (ADMIN ONLY, because it contains settings, storage and retention, the audit tail and source security settings, all of which are admin-only elsewhere (`api/audit.py`, `api/settings.py`, `api/storage.py`); the generation is audited through the W1a mechanism) returns `text/plain` with fixed, capped, deterministically ordered sections: header (format version `DCDASH-REPORT v1`, build id (part G), generated at in UTC and in the site time zone, uptime); environment (OS and runtime facts the app can see, Python, asyncua and pymodbus versions, database and TimescaleDB versions, time sync: database clock against app clock against the last server time seen); settings (allow-list, redacted); sources (type, enabled, URL with credentials scrubbed, security settings, status, last OK, last error); per-source health (reads per minute, error rate, the last distinct errors with counts and first/last time); points (counts by quality, the worst 20); the latest connection check; the journal tail (about 100 deduplicated events); scans; storage and retention jobs; the last 20 audit entries; recent API 5xx. `summary` is about 12 KB at most, `full` about 60 KB at most; above a limit the body is split into numbered parts (`PART 2 OF 3`) and the UI offers one Copy button per part. The last line is `END OF REPORT <short checksum of the body>` so a truncated paste is detectable. Redaction is ALLOW-LIST based (build sections from known-safe fields; never dump a config blob), reuses `scrub_url_credentials`, and a test feeds a source whose password, token and secret key appear everywhere they could and asserts none survives in `summary` and `full`. Never in a report: password hashes, the secret key, session tokens, private keys. Free text is the leak risk: asyncua and journal messages, job results, `last_error` and 5xx text quote `opc.tcp://<ip>:port`, host names, certificate CN/SAN and `urn:` application URIs. So every free-text field goes through `scrub_url_credentials(text, known=hidden_parts(config) of all sources)` (`core/audit.py`), and `mask=1` is a FINAL pass over the whole assembled body (regexes for IPv4, IPv6 and URLs, plus every host that appears in any source config, endpoint or certificate) replacing hosts and addresses with stable aliases (`HOST-1`, `HOST-2`, same alias throughout); the legend is shown only in the UI, never in the text. Compute the part split and the `END OF REPORT` checksum AFTER masking, and add `chars=N lines=N` to each part's footer (a model reading a paste cannot compute the checksum). A test asserts that no original host, IP or credential appears anywhere in the masked output, for both `summary` and `full`.

**D. Diagnostics page** (admin only; operators keep only the per-source "Check connection" action; under the Administer group or Settings): choose summary or full and mask, Build, a read-only text area with the size, Copy (per part) and Download .txt; a "Run connection check" per source showing the step list live; a shortcut "Check connection" on a source row. Follow the W6/W7 design rules and the Playwright name-substring rules; the e2e suite gains a spec for it.

**E. Offline path for when the web app itself is down (E-lite is in W8, the rest in W8b).** `scripts/collect-diagnostics.ps1` (PowerShell 5.1 compatible) and `scripts/collect-diagnostics.sh`: print and save `dcdash-diag-<timestamp>.txt` with service or container status, the last ~300 lines of each service log passed through the same scrubbing patterns, disk, time and port checks, DNS and TCP reachability for host:port pairs given as arguments, and database reachability. The workstation's install route (Docker, a VM, or native Windows services; backlog D) is not decided: detect what exists and degrade gracefully. No internet needed. The PowerShell scrubber is a second copy of `core/logscrub.py`: test both against ONE shared fixture file (`powershell.exe` is reachable from WSL).

**F. The protocol, written down: `docs/field-debugging.md`.** First-connection-day checklist (questions for the network and SCADA teams from backlog B and D: endpoint URL and port as seen from the workstation, direct server or gateway, security policy and mode, a read-only account, who trusts whose certificate, firewall rules, SCADA refresh rate, who to warn before scanning); how to produce the report and what to paste first (summary, then `full` or `source=N` on request); what never to paste (screenshots with credentials); the template for the owner's message to Claude (what I did, what I expected, what happened, report attached); how fixes come back (1: a value to type into the UI with the exact field names; 2: a small script or SQL file carried over RDP and run with a named script; 3: a rebuilt offline bundle, a separate future wave); and a note that reports contain addresses of an OT network, so the owner decides what leaves the workstation and `mask=1` exists.

**G. Version stamp.** The build id (git short sha plus build time, baked in at image build as a build argument) is returned by `/api/health` or a small `/api/version` and shown in Settings and in every report, so a report proves which code produced it.

**H. Fault injection in the dev simulator** so the whole loop is rehearsed before the real server exists. The OPC UA simulator gains dev-only switches (environment variables ONLY, read only by `backend/dcdash/simulator/`, the dev-profile service; no control endpoint, because this wave adds no network listener; a test asserts that api, collector and connectors never import the fault code): refuse an untrusted client certificate; require a username and password and reject a wrong one; offer only some security policies; answer slowly; drop the connection every N seconds; return Bad status codes on chosen nodes; report a skewed server time. Tests drive the connection check against each fault and assert that the failing step and the status code are named correctly. These switches must be impossible to enable in a production profile.

**I. Blind-read acceptance test.** In a scratch stack inject each fault of part H, produce the `summary` report, and give an Opus reviewer ONLY the pasted text (no repo, no tools) with one question: which step failed, what is the likely cause, what should the owner ask or change. It must get every fault right: run ONE Opus pass over all the reports with at most ONE report-fix round afterwards, then record what is still unclear as a known gap (an unbounded loop would eat the night). Keep the reports as fixtures in `docs/field-debugging-examples/` (they double as documentation). Anything the reviewer could not tell from the text is a gap in the report: fix the report, not the reviewer.

## Not in this wave
No call-home, telemetry or remote access of any kind (nothing leaves the workstation unless the owner copies it); no new network listener; the offline install bundle and Windows service packaging (backlog D) stay a separate wave; no writes to the SCADA.

## Review
An Opus plan review before coding; per-task Opus review for the migration, the redaction and the report endpoint's authorization and audit (security); the whole-wave review includes the blind-read results. Effort at most high.
