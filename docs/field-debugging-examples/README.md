# Field-debugging examples: what a report looks like for each failure

Fourteen real `summary` reports (the text the Diagnostics page builds and the owner pastes), one per failure the development simulator can produce, plus the healthy case and two masked ones. They are documentation and a regression aid: after a change to the report, build the same scenarios again and compare.

## How they were produced
A scratch Compose stack (project `dcdash_e2e_w8b_blind`, never the dev stack) with the OPC UA simulator at the host name `scada-gw.plant.local`, one source "SCADA main" with four mapped points, and the fault switches of `docs/field-debugging.md` ("Rehearsing a failure"). For each scenario: the simulator was recreated with the variables in the table, the source was disabled, the journal cleared, the source saved with the settings in the table and enabled, the collector polled for about 35 s, **Check connection** was run through the API, and `GET /api/diagnostics/report?detail=summary` was saved. Build ids and times, addresses of the scratch network (172.21.x.x) and the clock lines belong to that run. Values that are not part of the story: the audit tail lists the harness's own earlier steps (a person editing a source several times looks the same), the server certificate is called "dcdash-simulator" because the simulator makes it, and only 4 of the simulator's 60 points are mapped.

## Were they readable? The blind-read test
Before the last fixes, the same scenarios (build 23b4b1b) were each given to a separate Opus session that had NO tools, no repository and no memory of the project, with only the owner's message ("I set up the source with the details the SCADA team gave me and pressed Check connection. I expected values to arrive. It shows a problem. The report is below.") and the report, shuffled and renamed R01 to R14. It was asked for the failing step, the likely cause, the action and what the report left unclear. **All 14 answers were right**: step, cause and action named the injected condition (for example for the untrusted certificate: "the server refused the secure channel ... ask the SCADA team to move the certificate with thumbprint ... to its trusted list"). What the readers said was missing led to three report changes, made once: (1) the audit tail now says what a source edit changed (`changed: config.security_policy none -> basic256sha256`, secrets only as "changed"); it was the most repeated complaint (9 of 14); (2) a check whose points answer Bad names every distinct bad status with its first point, a hint per status, and the LATEST CHECK line says "but 2 of 4 points answered a Bad status"; (3) ENVIRONMENT lists the DNS servers of the container. **The files in this folder are the reports AFTER those changes (build of the final commit); they were not read blind again.**

## Known gaps (what the text cannot tell)
- The report cannot compare a clock with a reference outside this machine: the clock lines prove the container and the browser agree, not that either is right.
- A firewall that silently drops the first packet (no refusal, no answer) looks like a TCP timeout; it cannot be built without privileges, so it is not rehearsed.
- A server that refuses a login by closing the connection after an OpenSecureChannel ServiceFault (instead of an ERR message) loses its status code (backlog).
- `BadTooManySessions` (one session per poll plus checks against a server with a low limit) is a fault worth adding later.
- A source's password stored in the database cannot be recognised inside free text by the offline scripts (see `docs/field-debugging.md`).
